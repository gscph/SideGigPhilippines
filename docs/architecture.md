# SideGigPh architecture reference

The detail behind the short rules in [`CLAUDE.md`](../CLAUDE.md) → Architecture map. Read the section for the area you are changing, and keep it accurate when the code changes (CLAUDE.md keeps only the rules every session needs).

## Brand (Tarbaho)

Users see the app as **Tarbaho** (how kids say "trabaho"), and so does Android: the package id is
`com.tarbaho.app` (the Android app registered in Firebase, project `sidegigphilippines`). Solution, projects,
namespaces, the Firebase project and Azure names keep SideGigPh. The name shows from `AppTheme.Brand` (top bar,
language and sign-in screens, `BrandMark` on the splash), `ApplicationTitle` in `SideGigPh.Maui.csproj` (launcher
label), the window title in `App.xaml.cs` and the pre-Blazor splash in `wwwroot/index.html`; copy that names the app
says "Tarbaho" in `Copy.cs`.

- **Font:** DM Sans, a round geometric sans close to Airbnb's Cereal, set by `AppTheme.Style.FontFamily` (the
  skeleton's `BrandStyle.FontFamily`, default the phone's own font). The variable-weight Latin file (37 KB) ships
  in `wwwroot/fonts/dm-sans.woff2` with `DM-Sans-OFL.txt`, loaded by an `@font-face` in `app.css`, so the first
  launch offline already has it; characters it lacks (₱) fall back to the phone's font.
- **Taglines:** Pros "Find work near you" / "Umextra para sa Pamilya" (`Copy.RoleProfessionalHint`); Seekers
  "Find ___ nearby" / "May ___ para diyan" (`Copy.SeekerTagline`); before the role is known, `AppTheme.Brand.Tagline`
  says both.
- **Honorifics** (`Services/Honorifics`): workers are Manong, Kuya, Ate or Manang, never "laborers". The name never
  changes, only the honorific: a random one each launch on the `LaunchRouter` splash (both languages, since a first
  launch doesn't know the language yet) and in the search box until a trade is picked; after that the trade's own
  (`Honorifics.For`: Manong for construction (carpentry, masonry and the other building jobs are its jobs); Ate for errands; Kuya for everyday repairs and any
  new trade). Copy takes the word as `{0}`; English lines that want the plural ("Find Kuyas nearby", the empty search
  "No Kuyas…") pass `englishPlural: true` to `AppText.FormatHonorific`. Ate and Manang always stay in the rotation.
- Spell "maghanap" as one word. The logo is the **Folded T**: a slanted T for Tarbaho folded like a ribbon, four
  shapes in a 24-unit box (`AppTheme.Logo`) in one color at three strengths (full, 78%, 62% opacity), so it follows
  `Color.Primary` and still reads as three purple shades; also used by the launcher icon, both splashes and
  the Android notification icon (`ic_notification.xml`, white with the same alphas). Both splashes say
  **"Powered by AI"** small under the spinner (`AppBrand.SplashCredit`; the pre-Blazor splash in `index.html` in
  English). The native Android splash shows only the logo: Android 12+ crops it to the icon circle, so text can't go there. A small nav mark,
  the wordmark font and the final palette are still to come.

## Photos

- **Photos (MVP):** Azure Blob Storage (storage account `sidegigphbfb9`, also the Function App's own storage; container `photos`, blob `{id}.jpg` with a new random id per upload, readable by URL), written only through **`SideGigPh.Api`** (Azure Functions, isolated worker, .NET 10, published to the Function App `SideGigPhApi`, https://api.tarbaho.com/api/ (custom domain, [`azure/`](../azure/README.md#the-address-apitarbahocom))). The API checks the user's Firebase ID token, refuses a photo whose header says it is over 64 MP or 16,384px on a side before decoding it (`PhotoImage.IsTooBig`, `413 too-large`; a 48 MP phone photo fits), re-encodes every upload the same way (`PhotoImage`: upright, sRGB, at most 1280px on the long side and never enlarged, progressive JPEG quality 82, EXIF/GPS stripped; screens crop with object-fit cover). **Except a Skilled Worker's selfie** (their profile photo, `POST photos/selfie`, `UploadSelfie`): the phone makes it small (Android `AndroidPhotoPicker`, iOS `IosPhotoPicker`: upright, sRGB, at most 1280px, JPEG 82, no metadata) and the server only checks it (`SelfieJpeg.Check` = `SideGigPh.Contracts.Photos.SelfieJpegRules.Check`, the same rules the app's `ApiPhotoStore.SaveSelfieAsync` checks before sending so a bad file never goes up, plus one decode on the server: a real JPEG walked marker by marker to its end-of-image, 1 or 3 colour components, at most 2 MB and 1280px a side), refusing with `415 selfie-not-jpeg`, `413 selfie-too-big` or `400 selfie-broken` (the app shows `PhotoStoreFailure.Rejected` as "take the selfie again"); it is never resized or re-encoded, but its metadata is still taken out losslessly by an allow-list (frame, tables, restart interval and scans are kept; of the APPn segments only the bare JFIF header with its thumbnail cut off, an ICC profile and Adobe's 12-byte colour flag; comments, reserved markers and anything after the end-of-image marker go), so EXIF/GPS is never stored even from a modified app. A selfie blob carries `kind=selfie` in its metadata, and `PUT professionals/me` refuses a profile photo that changed and isn't the caller's selfie (`400 selfie-required`, `PhotoFunctions.IsSelfieOfAsync`); the app answers `PublishResult.SelfieNeeded` and opens the selfie step. A live listing's existing photo stays accepted. The selfie goes up through `IPhotoStore.SaveSelfieAsync` (skeleton default: `SaveAsync`). There is no duplicate-photo check (dropped 21 Nov 2026): every upload gets a new random id, so the same picture twice, or on two accounts, is two photos. Photos show straight from their public blob URL, so the container must allow blob-level anonymous read: the API switches a private `photos` container to it on first upload, and fails with a clear message when the account blocks anonymous access (`azure/cloudshell-setup.sh` turns it on; `cloudshell-verify.sh` checks it). **The storage connection string lives only in the Function App's settings (`PhotoStorage`)** or, on a PC, the git-ignored `SideGigPh.Api/local.settings.json`; never in the phone app. Setup and checks: [`azure/`](../azure/README.md). The app reaches it through **`ApiPhotoStore`** (`SideGigPh.Maui/Services/Api/`, registered in `MauiProgram` after `AddMobileAppTheme`, so it replaces the skeleton's `FilePhotoStore`): `POST photos` uploads, `POST photos/selfie` uploads a worker's selfie, `DELETE photos/{id}` removes, each with the user's ID token (`IIdentityProvider.GetIdTokenAsync`). The server's returned id is the photo id; photos show from their public blob URL. The API URL and blob base URL are constants in `MauiProgram` (not secrets).

## Tests

- **Tests:** **`SideGigPh.Tests`** (plain `net10.0`; xUnit 2, FluentAssertions **7.x** (8+ needs a paid licence for commercial use), `Microsoft.AspNetCore.TestHost`, coverlet). `Unit/` (by feature, fakes in `TestSupport/`, no network or database) and `Integration/` (the real `SideGigPh.Api` functions served in memory at the routes in their `[HttpTrigger]`s, the real stores on a fresh SQL Server database built like live is upgraded (`Sql/001-schema.sql`, then every `NNN-schema-*.sql` in order, then `004-config.sql`; `SchemaScriptTests` re-runs them to prove the guards), the real `FirebaseTokenValidator` with a test signing key, photos in an in-memory blob container, and per test person the app's real services and `AddSideGigPhApi` adapters; trait `Category=Integration`, skipped with a reason when no SQL Server: LocalDB on Windows or `SIDEGIGPH_TEST_SQL`). The app targets only Android/iOS, so the csproj **compiles `SideGigPh.Maui/Models/**` and `Services/**` (plus the `*Routes.cs`) into the tests by link**: keep pages' rules in `Services/` (pages aren't compiled there). Two test seams, unused by the app: `ApiOptions.Handler` (an `HttpMessageHandler` for `ApiClient`) and `FirebaseTokenValidator`'s optional `signingKeys`. Snapshot tests in `Unit/UpdateSafety/` fail on purpose when an id, JSON field name or error code changes. Coverage of the core code is ~100% (`coverage.runsettings`). How to run and what each folder protects: [`SideGigPh.Tests/README.md`](../SideGigPh.Tests/README.md); after a relevant change load the `run-tests` skill

## PR QA

Every pull request is checked **locally** by the `pr-qa` skill (`.claude/skills/pr-qa/SKILL.md`), right after it is
opened and again after fixes: a fresh QA agent reads the PR's own changes first, then follows the core features
(onboarding, search relevance, job posts and offers, chat) along the code the PR touches, runs `SideGigPh.Tests`
(`run-tests`) and the Android + API build check (`build-check`), walks the touched flows on an Android emulator when
one is already running, and reads the iOS paths (`Platforms/iOS`, `#if IOS`, the Firebase iOS adapters), since iOS
can't be built on the Windows PC. The main session confirms each finding, fixes it on the branch, and posts one QA
comment on the PR (the PR's changes / core features / Android / iOS / not checked). It also sets the version label.
GitHub runs no tests or reviews: its workflows are manual builds (iOS to TestFlight, Android AAB/APK) and the manual
API deploy.

## Key Ports (Interfaces)

**`IIdentityProvider`** (skeleton, `MobileAppTheme/Auth/`) — Auth abstraction; Firebase is one swappable adapter (see Auth → Switching the auth provider)
- `Methods` (which `AuthMethods` the provider supports)
- `SignUpWithPhoneAsync(string phoneNumber)` (sends the SMS code, for sign-in or linking; on Android the Firebase adapter does it through Firebase's own SDK in `AndroidPhoneVerification`, not the plugin: Plugin.Firebase (3.1 and 4.2) returns before Firebase answers and drops every answer but "code sent", so a refused send was silent, a number Android confirmed by itself never signed in, and a "code sent" that came while the app was in the background (reCAPTCHA page, reading the SMS: seen on Xiaomi) left no session, so the right code was refused. Each send now waits for Firebase's answer, keeps all of them per send (late answers to an older send are ignored, a resend to the same number uses the resend token), signs in by itself when Android confirms the number, asks again for the same number when the app comes back while a send still waits (Firebase drops a send's callbacks when the activity stops; `FirebaseAuthSetup` calls `ScreenBack` from `OnStart`, no second SMS), and the code check and `LinkPhoneAsync` use that send's credential. On iOS it is Firebase's own SDK too, in `IosPhoneVerification`: Plugin.Firebase 3.1 shows Firebase's web check (reCAPTCHA) over `UIApplication.KeyWindow`, which a scene-based app may not have, and the check comes back through the Encoded App ID URL scheme to the **scene**, which Firebase's app-delegate hooks never see, so the send waited until `SendCodeLimit`. `FirebaseAuthSetup` passes that URL to `Auth.CanHandleUrl` from MAUI's `SceneOpenUrl` / `OpenUrl`, and the app's `AppDelegate` passes Apple's push token and Firebase's silent push (`HandleApnsToken`, `HandleRemoteNotification`; `UIBackgroundModes` `remote-notification`), so with the APNs key in Firebase no web check is needed at all)
- `VerifyPhoneOtpAsync(string verificationId, string userEnteredCode)`
- `LinkPhoneAsync(string verificationId, string userEnteredCode)` (adds a verified number to the signed-in account, same uid; if another account has it, the same code signs in to that account instead, `AuthResult.SwitchedTo` / `SwitchedAccount`, never a second code; `AuthError.PhoneInUse` only where the adapter can't: Firebase does it through its own SDK, `AndroidPhoneLink` / `IosPhoneLink` (iOS: error 17025's updated credential), because Plugin.Firebase 3.1 drops the "updated credential" that signs in. Each phone failure logs Firebase's own code (`FirebaseAuthErrors.CodeOf`: iOS NSError domain + number, Android exception type), which the error reports keep while signed in)
- `SignInWithGoogleAsync()`, `SetDisplayNameAsync(string)`
- `SignInWithAppleAsync()` (iOS only, `IosAppleSignIn`: Apple's sheet through `ASAuthorizationController` with the SHA-256 of a one-time nonce, then `OAuthProvider.GetAppleCredential(idToken, rawNonce, fullName)` into Firebase, as Firebase documents it; Plugin.Firebase 3.1 sent Apple's token with no nonce, and its cancel had no "cancel" in its text. Closing the sheet (Apple error 1001) is `AuthError.Cancelled`)
- `GetCurrentUserAsync()`, `GetIdTokenAsync()` (the ID token for our own API as a Bearer header), `SignOutAsync()`
- **A dead session is signed out:** when the token refresh says the account is gone (deleted in the console or by Delete account elsewhere, disabled, revoked), `GetIdTokenAsync` signs out (`FirebaseIdentityProvider.IsDeadSession`; on Android the native `FirebaseAuthInvalidUserException` arrives unwrapped, so the type name is checked down the inner exceptions). Before this, such a phone stayed "signed in", every call went out without a token (401), screens showed empty and its error reports could not be sent either.
- **Nothing waits on the provider forever:** the Firebase adapter gives sending the SMS code `SendCodeLimit` (90 s, then a `TimeoutException` that `PhoneSignIn` shows as `AuthError.Network`; it counts as one of the day's codes only while `INetworkStatus` says online, `SmsSendLimit.FailedSendCounts`), the ID token `TokenLimit` (15 s, then logged as an error and the call goes out without one), because every API call waits for the token. The end of either interview waits for its saves at most `OnboardingFinish.WaitLimit` (15 s, `Services/OnboardingFinish`), and not when they failed, then opens the app anyway (the answers are on the phone and home loads its own data); both cases are logged, so they reach the error reports. The setup and Publish load only what is on the phone (`ProWorkspace.EnsureDraftLoadedAsync`, no network call), so they show at once on a slow connection; Pro home's `EnsureLoadedAsync` adds the chats and reviews. A session Firebase says is dead (`UserTokenExpired`, `UserNotFound`, `UserDisabled` while getting the token) is signed out, so the next screen asks to sign in instead of every call failing.

> **Naming:** user-facing text (`Copy`, `ReferenceData`, brand tagline) always says **"Skilled Worker"** / "skilled worker" (Taglish too), never "pro", "Professional" or "tradesman". Code keeps **"Professional"** (`ProWorkspace`, `ProfessionalListing`, `/professional` routes, `Professionals` table) for the side-gig service provider (aircon tech, plumber — and also non-trade pros like web developers or video editors), never "tradesman".

**`IOnboardingStore`**: the onboarding answers, saved on the device with no account (`Local/FileOnboardingStore`). It writes one JSON file in `FileSystem.AppDataDirectory`, using a source-generated serializer and an atomic write. There is no SQLite yet; add it when local data needs querying. Don't use the WebView's `localStorage`. **Android backup is off** (`android:allowBackup="false"`): Auto Backup restored an uninstalled build's answers and Firebase session onto a fresh install, which skipped the sign-in after the language with a session that then failed; an uninstall must mean a fresh start (the account's data is on the server).

**`IContactLauncher`** (skeleton): Call / Text a pro through the phone's apps (`MobileAppTheme/Services/Local/DeviceContactLauncher`, MAUI `PhoneDialer` / `Sms`). Android needs the `tel` / `smsto` `<queries>` in `AndroidManifest.xml`.

**`IChatRepository`** (`Api/ApiChatRepository`): **in-app chat**, one `Chat` per Seeker and pro (id `{proId}_{seekerId}`, carrying both names, the job from the Seeker's answers and the `LastMessage`) with its `ChatMessage`s (`Text`, or `Call` when the Seeker's Call button opened the dialer). `GetInboxAsync(personId, ChatSide, beforeChatId)` is one page of each side's Inbox, `Paging.Inbox` (30) chats, newest first (`GET chats?side=…&take=30&before={chatId}`; without `take` the server sends every chat, for app versions before paging): the workspace keeps the pages it loaded (`InboxPages`: a refresh re-reads the first page and keeps older pages below it; `ProWorkspace.HasMoreChats` / `MoreChatsAsync`, `SeekerWorkspace.HasMoreThreads` / `MoreThreadsAsync`) and both Inbox pages load the next one with `LoadMoreOnScroll` at the end; the badge counts the loaded chats; unread = the other person wrote last after this side's read time (`MarkReadAsync`); `GetMessagesAsync(chatId, beforeMessageId)` reads one page, `Paging.Messages` (20) per page (`GET chats/{id}/messages?take=20&before={messageId}`; without `take` the server sends every message, for app versions before paging): a chat page opens on the newest page, scrolled to the bottom, and loads the page before its oldest message when the person scrolls to the top (swipes down) (skeleton `LoadMoreOnScroll` `Edge="LoadMoreEdge.Top"`, which keeps the reader's place); the loaded messages live in **`ChatHistory`** (`Services/`: `FromLatest`, `WithOlder`, `WithLatest`, `With`; each workspace's `GetMessagesAsync` / `OlderMessagesAsync` / `NewMessagesAsync`). `Watch(chatId, lastMessageId, …)` gives live updates while a chat is open: it polls `GET chats/{id}` every `ApiChatRepository.WatchInterval` (5 s), skipped while the app is hidden (skeleton `AppVisibility`, set by `App`'s window `Stopped`/`Resumed`), and hands back the chat when its last message differs from the one the page shows; the page passes it to the workspace's `ChatChanged` and adds the newest page under what it shows (`NewMessagesAsync`). Only the Seeker can start a chat; the server stamps message times and takes the worker's name from their listing. **`IUserRepository`** (`Api/ApiUserRepository`, `users/me`): the signed-in person's `UserProfile` (account name/number, language, side (the earnings goal is no longer asked: the app sends `IncomeGoalId` null), and `ProfilePhotoId`: the account's one profile photo, the Seeker's own or the worker's listing photo, unique across accounts by `UX_Users_ProfilePhoto`), saved by `LocalAccount.SaveProfileAsync` at the role pick, the end of either interview, a language change and a profile-photo change; `SaveDeviceAsync(token, platform)` (`PUT users/me/devices`) registers this phone for notifications. **`IReviewRepository`** (`Api/ApiReviewRepository`): Seekers write one review per pro they chatted with, **only 24 hours after the chat started** (`ReviewRules.WaitAfterChatStarts` in `SideGigPh.Contracts`, shared by both sides; `SeekerWorkspace.CanRate` hides the Rate buttons and `ToRate` until then, and the thread shows `Copy.RateLater`; an earlier review can always be changed) (`SaveAsync` replaces; the server answers `403 no-chat` without a chat and `403 review-too-soon` before then); stars for ranking travel on each listing (`ProfessionalListing.Reviews`, averaged by SQL in the search query). Reviews about a pro survive their Start over.

**New-message notifications** (not SignalR: it only reaches an open app, which already polls): **`IPushNotifications`** (skeleton port, default `NoPushNotifications`; adapter `FirebasePushNotifications` in `MobileAppTheme.Firebase`, added by `builder.AddFirebasePush(channels)` in `MauiProgram` with the two Android channels `PushData.CustomersChannel` (loud) and `RepliesChannel` (quiet)). The server decides how loud: **a customer writing to a Skilled Worker rings** (title "New customer: …" on the first message); **a worker answering a Seeker only puts a red dot on the app icon** (Android: a silent tray line on the low-importance channel; iOS: badge only). One notification per chat (tag / `apns-collapse-id` = chat id), badge = the receiver's unread chats, data `PushData.ChatId` / `ProfessionalId` / `Side`, nothing shown while the app is open (it refreshes the Inbox instead). **`ChatAlerts`** (`Services/`, singleton) is the app side: `ProLayout` / `SeekerLayout` and the two full-screen chat pages `Attach` it (Inbox refresh on arrival, open the chat on a tap, `ChatAlerts.PathFor`), call `ShowUnread(Workspace.UnreadChatIds)` on every change (read chats leave the tray, the badge follows), and register the phone; the permission is asked only with a reason (`AskAsync`: Pro home opening with a live listing, the Seeker's `ThreadPage` after a send), never at first launch. Android needs `POST_NOTIFICATIONS`, `MainActivity` `LaunchMode.SingleTop`, and the `ic_notification` drawable (the logo path, white) named in the manifest. Server: `ChatFunctions.Send` → `ChatNotifier` (wording, English/Taglish from `Users.Language`) → `IPushSender` (`FcmPushSender`, Firebase Admin SDK, setting `FirebaseServiceAccount`; `NoPushSender` without it); a retried message id or a failed send never notifies twice or fails the message; dead tokens are deleted. Setup: [`firebase/README.md`](../firebase/README.md) → Notifications.

**`JsonFile<T>`** (skeleton, `MobileAppTheme/Services/Local/`): the one place that reads/writes an app-private JSON file (atomic temp-file write, corrupt file reads as missing, source-generated `JsonTypeInfo`). `FileOnboardingStore` and `FileConfigCache<T>` (the app config) use it.

**`LocalAccount`** (`Services/`, singleton, also registered as the skeleton's **`IAppAccount`** that `MePage` uses): the person on this phone, whichever side: app language (`SetLanguageAsync`, raises `Changed` for the layouts) and **switching side** (`SwitchSideAsync`, from the Me pages' `SwitchSideRow` through `/switch/{side}`: one account can be a household and a Skilled Worker; `Services/SideSwitch.MoveTo` sets `OnboardingState.Role`, the side the app opens on, and goes to that side's home when `HasFinished(role)` (`SeekerFinishedAt` / `ProFinishedAt`), else to its first question; a household whose worker side was never set up sees `Seeker/BecomeWorkerCard` ("Become a Skilled Worker", the look of Home's `PostRequestCard`) in place of the row, and Back on a new side's first question goes to `/switch/{the other side}` rather than the role fork (`SideSwitch.BackFrom`); the other side's answers, listing, chats and reviews stay; the server's profile gets the new side, and keeps the other side's photo until this side has one). The Me page has **no Start over** any more: `StartOverAsync` (deletes their photos, published listing, chats, reviews and profile, clears `IOnboardingStore`, both workspaces `Forget()`) is now only Delete account's path when there is no sign-in provider. Search leaves out the caller's own listing (`ProfessionalFunctions.HiddenInSearchAsync`). **Sign out** (`SignOutAsync`) signs out of the provider and makes both workspaces `Forget()` but keeps the answers on the phone; **Switching accounts** (`AccountSwitchedAsync`) makes both workspaces `Forget()` without signing out: adding a number that belongs to another account (often the person's own earlier phone sign-in) signs in to that account with the code they just typed (`AuthResult.SwitchedAccount`), and `AddPhonePage` and the interview's `NumberField` call it and go where a sign-in goes (`IAuthLanding`, or the name page), keeping the answers. Only where the provider can't switch (`AuthError.PhoneInUse`, iOS for now) do they offer "Sign in with this number" (sign out, then the sign-in page, which costs a second code). Delete account is `DeleteAccountAsync`.

**Ids:** the signed-in person's uid is their id on both sides (the server always takes it from the token, never the body): `ProWorkspace.MyId` (also the listing id, `Professionals.Id`) and `SeekerWorkspace.MyId`, both set when the workspace loads. Pages compare against those, never a literal. Only when no sign-in provider is registered do they fall back to the old fixed ids `ListingMapper.OwnListingId` (`"own"`) and `SeekerWorkspace.LocalSeekerId` (`"me"`).

**API adapters** (`SideGigPh.Maui/Services/Api/`, the only app code that talks HTTP): `ApiClient` (one `HttpClient`, the Firebase ID token on every request, `ApiOptions(ApiUrl, PhotoBaseUrl)`; its optional `Handler` is for tests only), `ApiProfessionalProfileRepository`, `ApiUserRepository`, `ApiReviewRepository`, `ApiChatRepository`, `ApiConfigRepository`, `ApiPhotoStore`, and `ApiMapping` (contracts ↔ `Models/`; models never get contract types). `AddSideGigPhApi(options)` registers them all in `MauiProgram`, after `AddMobileAppTheme`. Reads that fail (offline, server error) are logged and come back empty (`ApiClient.ReadAsync`); writes log and throw (`EnsureWritten`), and the pages already show a "didn't send / didn't publish" message. A listing sends photos by id (read from their blob URLs); the server stores ids and builds URLs.

**Round trips and caching** (each window is a named constant): `ApiProfessionalProfileRepository` keeps each page of search results for `SearchFreshFor` (60 s, per query and page: the server ranks, so a changed town, budget or job is a new request) and a listing for `ListingFreshFor` (5 min, filled by searches too; the Inbox and profile reuse it), both in `TimedCache<T>` (successful reads only); its publish/remove drops them. Each workspace's `RefreshActivityAsync` reads its lists side by side; tab pages call `RefreshIfStaleAsync` (skips within `ActivityFreshFor`, 15 s). The app's `HttpClient` asks for gzip (`ApiClient.GzipHandler`) and the API gzips JSON answers of 860 bytes or more (`GzipMiddleware`, which wraps the function's `ObjectResult`, because the Functions host writes the result after the middleware returns; 204/304 and callers that don't ask are untouched). Writes never re-read everything: a send, reply or mark-read updates the list from the server's answer (`Put`), and the chat page appends the saved message. Server side, `ListingCache` (`SideGigPh.AzureSQL`, `IMemoryCache`) keeps a trade's listings 30 s per instance (the next pages of a search rank that same list again) and is cleared by a publish, removal or review on that instance.

**Server** (`SideGigPh.Api` + `SideGigPh.AzureSQL`): one function class per area (no route may start with `admin`: the Azure Functions host keeps that prefix for its own admin API and never loads such a function, so live it answers 404 while the in-memory test host serves it; the operator routes are `ops/…`, guarded by `ApiWiringTests.NoRoute_StartsWithAdmin`) (`UserFunctions`, `ProfessionalFunctions`, `ReviewFunctions`, `ChatFunctions`, `PhotoFunctions`, `ConfigFunctions`, `ErrorReportFunctions`), each checking the token first (`FirebaseTokenValidator.GetUidAsync` / `GetCallerAsync`, which also gives the verified `phone_number`) (the one public route is `GET config`, reference data read before the account is ready; `ApiWiringTests.PublicRoutes`), then calling a store (`UserStore`, `ProfessionalStore`, `ReviewStore`, `ChatStore`, `PushDeviceStore`, `ConfigStore`, `OtherJobNoteStore`, `ErrorReportStore`) that holds the data rules and answers with contracts or an outcome enum. Errors answer `{ "error", "detail" }`: `ErrorDetailsMiddleware` turns any exception into `500 exception` (or `400 bad-body`) with the stack trace in `detail` while `ApiResults.ShowDetails` is on (MVP debugging; on unless the Function App setting `ShowErrorDetails` is `false`: set that before launch), and the app logs the whole answer (`ApiClient.EnsureWrittenAsync`). Multi-row writes use `db.InTransactionAsync` (retry-safe on Azure SQL); a caller's own data sits under `…/me` / `…/mine` routes. Writes a script could repeat are limited per account by **`CallerLimits`** (in memory per instance, sliding window; `Limited`: chat messages 30/min, new chats 20/h, "Others" notes 20/h, error report batches 12/h, photo uploads 10 per 15 min, reviews 30/h): past it `429 too-many-requests` (`ApiErrors.TooManyRequests`), which the app shows as its usual didn't-send message. Search ids that can't be a trade or area find nobody without a database read or cache entry. "Others" (`OtherWork.TradeId` `other`, and each trade's `…-other` job) is accepted as a listing's and a job post's trade and job; search takes the Seeker's typed `otherText` and `SearchRanker.OtherWordsMatch` puts workers whose `ListingDto.OtherWork` shares its words first (the job-post feed still orders "Others" posts by distance only). Settings: `PhotoStorage`, `SqlDatabase`, `FirebaseProjectId`, `FirebaseServiceAccount` (notifications; optional), `ShowErrorDetails` (optional).

**Error reports** (`Services/Diagnostics/`, so we can fix what we can't reproduce, like a phone that hangs after the interview's Done): **`ErrorLog`** (singleton) keeps the problems the app had on this phone in `diagnostics.json` (port **`IErrorLogStore`**, `Local/FileErrorLogStore`, kept by Start over): errors any code logs (**`ErrorLogLoggerProvider`**, an `ILoggerProvider` service; the app's own information and warnings become trail lines), **every failed API call, logged once by `ApiClient`** whatever the caller does with it (no answer: `SendWithRetryAsync`, any failure but a cancel the caller asked for; an error status: `ThrowIfFailedAsync`; `ReadAsync` logs only an answer it can't read; the error-report send passes `logFailure: false` so it never reports itself), so a page that turns a failure into "didn't post" or a workspace that turns it into a result never needs to log it (the exception is marked, `ErrorLog.MarkReported`, and logging it again as an error adds a trail line instead of a second report; any other exception the same catch sees is still its own report), crashes and unobserved task errors (**`ErrorReporting.Start`**, from `App`; a crash saves the log before the app closes), on iOS an Objective-C exception on its way into .NET (`Crash.ObjC`, an error) and a .NET exception thrown into native code (`Crash.Native`, a crash, the log saved at once) (**`Platforms/iOS/IosCrashCapture`**, from `MauiProgram` right after the app is built), on Android what .NET never sees (**`Platforms/Android/AndroidCrashCapture`**, from `MainApplication.OnCreate`: a Java exception nothing caught, source `Crash.Java`; ## Versioning

- **One source:** `Directory.Build.props` at the repo root. `AppVersionNumber` is SemVer `major.minor.patch`:
  **worked out from the PRs squashed into `main`**: a PR with the label **`minor`** (or a `feat: …` title) is the next
  minor (`0.1.4` → `0.2.0`), **`major`** (or `feat!: …`, any `type!:`) the next major (→ `1.0.0`), any other PR the
  next patch (`0.2.0` → `0.2.1`). `.github/scripts/app-version.sh` walks the merges from the last commit that changed
  `AppVersionBase` (`major.minor`, now `0.1`; editing it sets the version by hand), asking GitHub for each one's PR
  labels (`GH_TOKEN`; titles only without it), and the app build (`build.yml`, full history checked out) passes the
  result as `AppVersionNumber`, so each build knows the version it ships. **App only:** the API deploy doesn't pass
  it, so the API (and a PC build) is `AppVersionBase.0`.
  **When opening a PR:** label it `minor` for a feature people will notice, nothing for anything smaller, `major`
  only for a breaking change or a milestone (the owner can change the label before squashing). The
  [PR QA](#pr-qa) adds `minor` / `major` to a PR that has neither. `AppVersionStage` is the pre-release stage
  (empty since the Play Store launch; `rc` for a pre-release), and `BuildNumber` comes from CI
  (`-p:BuildNumber=${{ github.run_number }}`; `0` on a PC). Together they make `AppVersionLabel`: `0.2.3` from CI,
  `0.1.0` on a PC, `0.2.3-rc.12` in a pre-release. Nothing else holds a version.
- **Where it goes:** the app's csproj maps it to the store fields (Android `versionName` = the whole label and
  `versionCode` = the build number; iOS `CFBundleShortVersionString` = the three numbers, since Apple allows nothing
  else, and `CFBundleVersion` = the build number). `Directory.Build.targets` (`StampBuildInfo`, on for the app and the
  API) writes the label, the git commit (`git describe`, `-dirty` with local changes) and the app's channel into the
  assembly as `[AssemblyMetadata]`.
- **App:** `Services/Diagnostics/BuildInfo` (`BuildInfo.Current`) reads the stamp. `AppTheme.Brand` passes
  `BuildInfo.Current.Label` (`v0.1.0-rc.12`) as `AppBrand.Version`, which the skeleton shows as a muted caption under
  the spinner of `SplashScreen` (the launch splash and the busy splash) and beside the logo in `AppTopBar`. The
  pre-Blazor splash in `wwwroot/index.html` is static HTML and shows no version; it is on screen for a moment only.
- **Error reports** carry `AppVersion` = `0.1.0-rc.12 (12)` (label + store build), `CodeVersion` and `Channel`
  (`DeviceStamp`, unchanged columns).
- **API errors name both builds.** `ApiClient` sends `X-App-Version: 0.1.0-rc.12 (beta; 48466c9)` on every call
  (`ApiOptions.ClientVersion`, header names in `Contracts.ApiHeaders`). The server's `ErrorDetailsMiddleware` puts
  `X-Api-Version` (`ApiVersion.Current`, e.g. `0.1.0-rc.57+48466c9`) on every answer, logs every crash with the
  caller's app version, and logs a warning for every refusal a function answers (400, 403, 409, 429, 5xx; not the
  everyday 401 and 404). On the phone a failed call is logged as `API 0.1.0-rc.57+48466c9: couldn't … : 500 …`, and
  that log line becomes an error report, so one row in `ErrorReports` says which app build met which API build.
- **The app and the API count builds separately** (each workflow's own run number), because they ship separately.
- **A PC build over a CI build:** Android refuses to install a lower `versionCode` over a higher one, so a tester's
  phone with a CI build needs that build uninstalled before a Visual Studio build goes on it.

## Usage analytics (our own)

No analytics SDK and no A/B tests: two questions only, **do matches happen** and **do they repeat**, answered from
one table.

- **Table** `dbo.app_events` (`032-schema-app-events.sql`): `event_id` (unique, so a retry is kept once),
  `event_name`, `source` (`server` / `app`), `user_id` (the opaque uid; NULL after Delete account), `user_type`
  (`customer` / `worker`), `session_id`, `service_category` (trade id), `area` (town id), `search_term`,
  `result_count`, `minutes_to_match`, `reason`, `request_id` (the job post's id: request → match → job), `app_version`,
  `client_ts` (app events), `server_ts` (arrival). View `dbo.v_events` adds `event_ts_ph` (UTC+8) and `week_start_ph`
  (Monday). EF maps it as `AppEventRow` (snake_case columns).
- **Server events** (`SideGigPh.AzureSQL/AppEventStore`, scoped): `LogAsync(new AppEvent(name) {…})` is one
  parameterised `INSERT` after the store's own save (never inside its transaction), catching and logging any failure
  so the request still succeeds; it gives up after `GiveUpAfter` (3 s), so a slow database never holds the answer
  back for long (the same limit on `HasAsync`). Where: `UserStore.SaveAsync` (`sign_up`, the first time a profile is saved with a
  side), `JobPostStore.AddAsync` (`request_created`), `JobPostStore.PickAsync` → `LogMatchAsync` (`request_matched`;
  `rehire` when the household already completed a job with that worker), `PickedJobStore.MarkDoneAsync` →
  `LogCompletedAsync` (`job_completed` when the second side marks done; `worker_first_job`), `ProfessionalStore.PublishAsync`
  (`worker_profile_complete`, first live listing only), `SafetyStore` (`report_user`, `block_user`, with the report's
  reason). Each logs only on the real change, so a repeated write (`ApiClient.WriteTries`) never counts twice;
  "first time" events also check `HasAsync`.
- **App events** (`SideGigPh.Maui/Services/Analytics/`): `TarbahoAnalytics.Search(...)` from `SeekerWorkspace.SearchAsync`
  once results loaded (a read that failed returns the shared `SearchResult.Empty` and isn't counted; the same search
  again in one session isn't either). Events go to `pending-events.json` (`IPendingEventStore` /
  `FilePendingEventStore`) on the thread pool; at most `MaxQueued` 500, `KeepFor` 7 days. `AnalyticsUploader`
  (started by `App`, like `ErrorReporting`) sends the 50 oldest through `IAppEventRepository` / `ApiAppEventRepository`
  (`POST events`, not logged by `ApiClient` when it fails: offline is normal) and removes exactly those once the server
  answered `202`; a `400` drops the batch; anything else stops until the next try. Tries: 45 s after launch, every
  15 min while on screen, and when the app goes to the background; only while signed in. A new session id after 30+
  minutes away (`App` → `AppShown` / `AppHidden`). There is no WorkManager: uploads happen while the app runs.
- **`POST events`** (`AppEventFunctions`): signed in, `CallerLimits` `AppEvents` (30 batches an hour), a JSON array of

  `user_type` `customer` (only households search); `client_ts` over 5 minutes ahead or 7 days old becomes NULL; text cut to its column, search words

- **Reports:** `analytics/weekly.sql` (7 questions; run one day after the week ends; `AppEventTests` runs it),
  `analytics/retention.sql` (the 12-month delete by hand). Privacy policy §3.3 and the Play Data safety answers
  describe it: change them together.

## Blocked words

Text other people read is checked for vulgarity, sexual words, slurs and insults in English, Tagalog/Taglish and
common Bisaya, by one shared class both sides run: `SideGigPh.Contracts/Moderation/BlockedWords.cs`.

- **The lists** are embedded text files next to it: `blocked-words.txt` (`[whole]` entries match whole words or
  phrases, `[part]` entries match inside a word, for words never innocent inside another) and `blocked-patterns.txt`
  (regexes on the raw text: symbol art like `8==D`, emoji, and words whose rude and normal forms differ by context,
  like `leche` vs `leche flan`). Edit them like any code change; no SQL, no app config.
- **Normalizing** comes before matching: NFKC, accents and invisible characters dropped, lower case, Cyrillic/Greek
  look-alikes mapped, spelled-out runs joined (`p u t a`), digits and symbols read as letters inside a word
  (`put@`, `g@g0`, `b0b0`; never in a quantity like `1500` or `10am`), separators inside a word dropped (`p.u.t.a`),
  repeated letters collapsed. `1` and `|` are read as `i` and again as `l`; whole entries are also matched with `v`
  read as `b` (`vovo`).
- **Everyday words that look alike pass**: `puto`, `tae`, `bakla`, `atay`, `supot`, `Taytay`, `poso negro`.
  `SideGigPh.Tests/Unit/Moderation/blocked-words-samples.txt` holds `[block]` and `[allow]` samples that
  `BlockedWordsTests` runs, and the test also checks that no label in `004-config.sql` is caught, so a new job name
  can't be refused.
- **The server** (`JobPostStore`, `ReviewStore`, `PickedJobStore`, `FeedbackStore`, `UserStore`) refuses a rude post
  description, offer note, review comment or reviewer name, household rating comment and feedback title or details
  with its usual `invalid` answer; a rude new display name keeps the old one.
- **The app** checks first so the person can fix it: `Services/RudeWords.In` turns the box red with
  `CommonCopy.RudeTextNote` ("Please take out the rude words." / "Pakitanggal ang mga bastos na salita.") and keeps
  send off (`JobBoard.Missing` / `MissingText`, `JobBoard.CanOffer`, `FeedbackBoard.CanPost`, `WriteReviewPage`,
  `PickedJobCard`). The skeleton's `NamePage` asks the port `ITextCheck` (default `NoTextCheck`; the app registers
  `RudeWordsCheck`).

## Feedback board

- **What:** both sides open it from the Me page (`SeekerRoutes.Feedback` / `ProRoutes.Feedback` →
  `/feedback/{side}`, `Components/Feedback/FeedbackPage`, full screen): suggestions with a vote button, **most voted
  first** (open and planned ones, then finished ones), in pages of `Paging.Feedback` (20). The board shows no names.
- **Suggesting (`SuggestPage`, `/feedback/{side}/new`):** write a title (6–100 characters) and optional details →
  the app asks `GET feedback/similar?q=…` → when look-alikes exist, **"Is it one of these?"** lists them
  (`SimilarSuggestion`): "Yes, same idea" adds the person's vote to that one and posts nothing; "No, mine is
  different" posts it. With no look-alike it posts at once. The writer's own vote is the first.
- **Look-alikes (`SideGigPh.AzureSQL/FeedbackMatch`):** titles are compared by the words that carry meaning (small
  English and Tagalog words and wish-list words like "add", "sana", "po" dropped, plural "s" ignored); two are
  similar when at least half of the shorter one's words are in the other (`MinScore`). The server compares against
  the 500 most voted (`FeedbackStore.MaxCompared`). No AI: the person confirms the match.
- **Rules (server, `FeedbackStore`):** one vote per person (`PK_FeedbackVotes`; voting twice changes nothing);
  `Votes` is recounted from the vote rows on every change; the same title from the same person again answers with
  the first; the writer may delete their own only while nobody else voted; a report adds a row to `Reports`
  (`SubjectId` `feedback:{id}`); `declined` and `hidden` leave the board. Limits: 10 suggestions and 120 votes an
  hour per account. **Delete account** removes the person's votes (counts follow) and clears `AuthorUid` on their
  suggestions, which stay.
- **App (`Services/FeedbackBoard`, singleton, port `IFeedbackRepository`, adapter `ApiFeedbackRepository`):** holds
  the loaded pages; a vote shows at once and is put back if it didn't reach the server; a new suggestion goes on top
  of the list; the order otherwise stays put while on screen and is re-sorted on the next load.
- **On the web (`SideGigPh.Api/SuggestFunctions`, `SuggestPage`, public `GET` / `POST suggest`, `POST suggest/{id}/vote`):**
  the same board as a plain HTML page (no script, the legal pages' look), the "Feedback URL" Play testers get:
  `https://api.tarbaho.com/api/suggest`. Upvote on every row; a new
  idea first shows its look-alikes to upvote and only "None of these, post mine" posts it. No sign-in: a visitor is
  a random id in the cookie `tarbaho_voter` (1 year), stored as `web-<id>`, so one browser has one vote per
  suggestion. Posts are marked `Source = 'web'` and show at once, like the app's; spam is held back by a hidden
  field bots fill in and by `CallerLimits` per IP (the last `X-Forwarded-For` entry; 5 posts and 60 votes an hour)
  and in total (60 posts an hour). The operator hides what doesn't belong with `Status = 'hidden'`.
- **Operator:** `UPDATE dbo.FeedbackPosts SET Status = 'planned' WHERE Id = …` (or `done`, `declined`, `hidden`);
  top of the board: `SELECT Id, Votes, Status, Side, Source, Title FROM dbo.FeedbackPosts ORDER BY Votes DESC`.

## Badges (worker verification)

Four badges, each approved by a person at Tarbaho: **ID Verified** (a government ID; read by AI first to help the
checker), **NBI / Police Clearance** (kind `clearance`, an NBI or police clearance, checked by a person only;
`031-schema-clearance-badge.sql` widened the `Kind` check; **the checker approves only a genuine clearance in the
worker's name, NBI under 1 year or police under 6 months old, showing no record** ("No record on file"), and
rejects anything else with a neutral reason ("We can't approve this clearance"), never naming a record; its own
consent line `BadgeConsentClearance` says a record on it is seen only for the badge; **the server reads its QR code**
(`SideGigPh.Api/ClearanceQrReader`, ZXing.Net on the stored JPEG, free and local, no AI) into `ScannedQr`, shown only to
the operator: `ClearanceRules.OfficialLink` / `IssuerOf` say whether it is an NBI (`nbi.gov.ph`) or PNP
(`pnpclearance.ph`, `pnp.gov.ph`) web address, linked to open and compare, else a red "may be fake" note; never a
reason to refuse an upload (a crumpled paper may not read) and never an approval (a QR can be copied onto a fake);
**approving needs the "valid until" printed on the paper**, typed by the operator (`VerificationDecisionRequest.ValidUntil`,
today to a year and a week ahead, `ClearanceRules.IsValidUntilAllowed`, else `400 valid-until-needed`), kept after
the decision (`WorkerVerifications.ValidUntil`, `034-schema-clearance-valid-until.sql`): **the badge lapses the day
after** (`ClearanceRules.HasLapsed`, Philippine date; `ProfessionalStore` leaves it off the listing), the worker's
Badges page shows it as `BadgeState.Expired` ("Expired", amber) and a new one can be sent; while approved the row

## Cold starts and double taps

- **Warm-up:** the Function App (Flex Consumption) and the serverless database both go cold when nobody uses them; the first search then waited ~15 s on 4G. `Services/ServerWarmup` (rule, tested) calls the `IServerWarmup` port (`Api/ApiServerWarmup` → `GET warmup`, signed-in, `204`) from `App` when the window opens and on `Resumed`, at most once per `ServerWarmup.IdleAfter` (5 min). The function checks the token (which also loads Google's signing keys) and `WarmupStore.WakeAsync` runs `SELECT 1`, skipped when that instance already did within `WarmupStore.AwakeFor` (1 min). Signed-in only, so nobody outside can keep the database awake and billed. A failed warm-up is only a trail line. The first wake on each instance also compares `dbo.SchemaChanges` with `SchemaScripts.Required` (every `NNN-schema-*.sql` after 001, checked against the folder by `SchemaCheckTests`) and, if a script was never run, logs an error and saves an `ErrorReports` row naming it (on 15 Nov a missing `011-schema-safety` made every search and Inbox answer 500 for a morning).
- **One tap, one call:** every tap handler that calls the API, the sign-in provider (SMS costs money) or the camera returns early while `_busy`; `Disabled="_busy"` alone is not enough, since a second tap can arrive before the re-render. Handlers catch failures into a message (`MePage` Delete account shows `CommonCopy.DeleteAccountFailed`).
- **A screen that throws:** `MainLayout` wraps the page in `AppErrorBoundary` (skeleton), which logs the exception through `ILogger` (so `ErrorLogLoggerProvider` makes it an error report) and shows `CommonCopy.ScreenBroke` with a button back to `/`; any navigation clears it. When the exception is a lost connection (`NetworkErrors.IsNetwork`: an `HttpRequestException` with no status code (the `ApiClient` wraps Android's socket errors in one), a `WebException`/`SocketException`, a request timeout; a server's error answer, a plain cancel and file errors such as "No space left on device" are not), it shows `CommonCopy.NoConnection` with **Try again** instead, which rebuilds the same page so it loads again. **What "offline" means:** `INetworkStatus` (`DeviceNetworkStatus`) is offline when MAUI `Connectivity` says there is no network, **or** when the last API request got no answer (`ApiClient` reports each request: `NoAnswer()` for `NetworkErrors.IsNetwork`, `Answered()` for any answer, even an error status) and none has been answered since; a change of network clears it. **Not offline by mistake (iOS):** an answered request counts the phone online even when `Connectivity` says no network (iOS reachability can be wrong or stale, e.g. after the background or on a VPN) until the next change of network; a request with no answer within `DeviceNetworkStatus.SettleAfterChange` (10 s) of a change of network (5G → Wi-Fi breaks the requests already on their way, TLS handshakes included) doesn't count, nor one the app's trip to the background broke (`AppVisibility.TimesHidden` changed while it was on its way: iOS drops a suspended app's connections), nor iOS's own timeout (`NSURLErrorTimedOut`, -1001); and the strip, once shown, re-checks every `ConnectionBanner.RecheckEvery` (5 s) so it hides on a recovery the platform never announced. So broken DNS or a captive Wi-Fi (connected, nothing gets through) still shows the strip and "No internet + Try again". While the phone is offline, `ConnectionBanner` shows a gray `CommonCopy.Offline` strip above the page once the phone has been offline for `ConnectionBanner.ShowAfter` (3 s, so a one-second 4G drop doesn't move the page under the person's finger) and hides it when the connection is back; the strip is sticky (`--app-offline-banner-height`, the top bar sits under it through `body:has(.app-offline-banner)`), so it shows on a chat that opened scrolled to its end. `BusyOverlay` swaps its rotating lines for `CommonCopy.BusySlow` (offline: `BusyOffline`) once a wait passes `SlowAfter` (12 s). A chat's send error is `ChatComposer.Error`, inside the pinned box (an alert above it was covered by it). Search hides its "0 for you" line while offline. **Empty or offline:** reads log and come back empty, so an empty list can mean "no internet". A list read from the server passes `OnRetry` to `EmptyState` (search results, both Inboxes, my posts, the Requests feed, a post's offers, My offers); while offline it shows `CommonCopy.NoConnection` with a WifiOff icon and **Try again** instead of its "nothing here" line, and calls `OnRetry` by itself when `INetworkStatus` says the connection is back. An `EmptyState` without `OnRetry` (photos not yet picked) never changes. **Slow 4G:** `ApiClient` cancels a GET after `ReadTryLimit` (30 s, so two tries match the old 60 s timeout a cold server and paused database may need) and tries once more (`ReadTries` 2), then fails as a lost connection (`HttpRequestException` without a status); writes (POST/PUT/DELETE) are sent once, since a retry could repeat them, except the ones the server takes twice without harm (`ApiClient.SendRepeatableAsync` / `SendJsonAsync(..., repeatable: true)`: a photo upload, a new or edited job post, which the server answers with the post already there): when the connection drops before any answer (not a timeout) they go once more (`RepeatableWriteTries` 2) with a fresh copy of the body. iOS sends a write on a kept-alive connection the server already closed after a pause (the photo picker, a long form) and, unlike for a read, doesn't retry it itself, so without this a post right after adding a photo failed as "no internet". When a next page never arrives, `LoadMoreOnScroll` stops loading on its own and shows `CommonCopy.LoadMoreFailed` with **Try again**. **Pushes while open:** `ProLayout` / `SeekerLayout` refresh the Requests feed / my posts (with the Inbox) when a notification arrives in the foreground. On Android, a lost connection that escapes every catch reaches `AndroidEnvironment.UnhandledExceptionRaiser`, which marks it handled (reported as `Crash.Network`, the app keeps running); anything else still crashes.

  - `SearchIntentParser`: free text → trade + (when one clearly fits) job, matched against both languages' category/job labels, category hints and `TradeWords` synonyms (tubero, kuryente, hinang, masahe…). Generic job words (sira, repair, install…) count half toward the trade, and a word found only in one of a trade's job labels counts 0.9 (`JobOnlyWordWeight`), so a trade's own word wins ("kotse" is the Car Mechanic before Errands' car cleaning); a tie or weak match returns no trade plus the closest ones, and the UI asks "which kind of pro?". Add a synonym to `TradeWords` when users type a word we don't catch.
  - `SearchRanker` (**server**, `SideGigPh.AzureSQL/SearchRanker.cs`, over `RankCandidate`s (a `ListingDto` + server-only `WorkerSignals`: chats received/answered in 90 days and average first-reply minutes from `Chats.ProfessionalRepliedAt`, `Users.LastActiveAt` (stamped at most hourly by `UserStore.TouchAsync` when a worker reads their Inbox), account age), with `RankScales` from the config; `RankedResult.Page(skip, take)`). Filters: **exact job only** (no fallback; `SearchPageDto.ServiceFallback` is always false, kept for old apps); grouped "goes to your town" then "other towns nearby" (= other towns in the Seeker's area; workers only in other areas are left out). Then a **0–100 score** inside each group (`RankScore`, every part a 0–1 feature × a named weight): reviews 30 (Bayesian stars 22 + log review count 8), responsiveness 20 (smoothed reply rate 12 + reply speed 8), activity 20 (weekly half-life 14 + tenure 6), budget fit 20 (the worker's price for the job vs the top of the Seeker's range), experience 10; new workers start from neutral priors. **Paid boosts are never part of the score**: they will be labeled sponsored slots placed after ranking, behind a quality floor. Full rationale and the boost plan: [`docs/search-ranking.md`](search-ranking.md).
  - `ProfessionalSearch` (app) asks the server for one ranked page at a time (`SearchAsync` the first, `MoreAsync` the next after what is shown); a page that didn't load (offline) leaves the results as they are.
- **Results page** (`/seeker/search`, `Search/SearchPage`): laid out like Airbnb's list (`docs/ux/airbnb-2026-11-18/airbnb-11`): two groups under headings that say where, "9 skilled workers in Angono" then "3 more in towns nearby" ("None in Angono yet · 3 in towns nearby" when the town has nobody; `ResultText.InTownHeading` / `NearbyHeading`), no summary or explainer line; each result is a divider-separated `ResultRow`: a small rounded-square photo (`result-thumb`), line 1 "Aircon Technician in Angono" (the Seeker's town when the worker goes there, `ResultFacts.TownId`) with ★ 4.9 (12) or "New" on the right, line 2 the name muted, line 3 facts joined by · (years · services done · the first badge, `ResultFacts.Facts`, `ResultText.FactsLine`), the price for the searched job in money green + "per service", and at most one gray pill, "Fits your budget"; the whole row opens the profile (search no longer uses `ProCard`, which stays for the worker's own preview and `Dense` on a post's offers); rules tested in `Unit/Search/ResultFactsTests`.

## Auth

Auth is provider-neutral. The contract and screens live in the skeleton; the vendor is an adapter in its own project.

- **Contract (skeleton, `MobileAppTheme/Auth/`):** `IIdentityProvider` (phone code, Google, current user, sign-out, and `Methods`, the `AuthMethods` it supports) with `AuthUser`, `AuthResult` and `PhoneVerification`. A failure is an **`AuthError`** (`Cancelled`, `Network`, `InvalidCode`, `InvalidPhoneNumber`, `PhoneInUse`, `TooManyAttempts`, `Misconfigured`, `NotAvailable`, `Unknown`) plus the provider's raw `Detail` for logs. The UI shows `AppText.Describe(error)` (`CommonCopy`, English/Taglish), never provider text.
- **Screens (skeleton, `MobileAppTheme/Components/Auth/`):** `AuthPage` (route **`/verify`**: brand + tagline, then only the methods the provider offers: the phone code first for everyone, then "or" Apple/Google; on the code step Apple/Google come back under "Still no code? Sign in another way:" after **`CodeFallback.ShowAfter`** (60 s from the first code, kept through a resend) or at once when today's codes are used up, since an SMS can be filtered by the carrier or refused by the provider), `NamePage` (**`/verify/name`**, once when the account has no name), `AddPhonePage` (**`/verify/phone?then=…&back=…&skip=true&later=…`**, links a verified number to the signed-in account; Back goes to `back`, else home; `skip` adds "Do this later" → `then`, for an early ask a later page repeats; `later` adds it → that path, for a page that needs the number: Publish sends it to Pro home, whose purple not-live banner then says "Confirm your number to publish", so a worker out of SMS codes for today is never stuck), `PhoneSignIn` (`LinkToCurrentUser` for linking; rationed by **`SmsSendLimit`**: a new code only 360 s after the last, at most 3 in 24 h per phone, kept in Preferences by `PreferencesSmsSendHistory`, with a countdown on "Send a new code"; the sixth digit sends the code without a tap; signing in, it also goes on by itself once the provider has someone signed in with the number the code went to, since Android may read the SMS and confirm the number while the code step is open, and the Firebase adapter then answers a typed code refused as used with that sign-in) and `GoogleSignInButton`. **`SignInGate`** (`MobileAppTheme/Auth/`) is what pages ask: it returns the missing step (sign in, name, phone) or null, and lets everyone through when no provider is registered. Routes are in `AuthRoutes`.
- **App hooks:** `IAuthLanding` says where to go after sign-in. SideGigPh keeps the skeleton's `HomeAuthLanding` (`/`): the launch router restores a worker's live listing on a phone with no answers (`ListingRestore`) and resumes onboarding or opens their home. `IPhoneNumberFormat` reads typed numbers into E.164; SideGigPh's `PhilippinePhoneNumberFormat` accepts 0917… / 917… / +63 917… and sets the optional `Region` ("Philippines (+63)"), shown read-only above the number like Airbnb's Country/Region box. Skeleton defaults (`TryAdd`): `NoIdentityProvider` (no sign-in, `Methods = None`), `HomeAuthLanding` (`/`) and `E164PhoneNumberFormat`.
- **Adapter: `MobileAppTheme.Firebase/`** (Android/iOS MAUI library, `Microsoft.NET.Sdk`, not Razor, so no WebView asset clash). `FirebaseIdentityProvider`, `FirebaseAuthErrors` (status-code decoding) and `FirebaseAuthSetup`: `builder.AddFirebaseAuth(GoogleWebClientId)` in `MauiProgram` initializes the SDK in the platform lifecycle (wrapped, so a missing config doesn't crash launch) and **replaces** the skeleton's `IIdentityProvider`. `GoogleWebClientId` (the web OAuth client, client_type 3, from `google-services.json`) is a constant in `MauiProgram`.
- **Auth error policy:** an adapter never reduces an auth-infra exception to a bare message. It logs the full exception (type + stack) to Logcat/Output and returns an `AuthResult` with a mapped `AuthError`. For Google sign-in, `FirebaseAuthErrors.FromGoogle` parses the Google Play status code out of the exception message (which is just `"7:"`, `"10: …"`), with no dependency on the Play-services binding: `7` → `Network`, `10` DEVELOPER_ERROR / `12500` → `Misconfigured`, `12501` → `Cancelled`. A wrong SMS code (`FirebaseAuthException` `InvalidCredential`) → `InvalidCode`. `SignUpWithPhoneAsync` logs then throws (fail fast): its time limit as `TimeoutException` (the SMS may still go out), anything else as the skeleton's `AuthException` with the mapped `AuthError` (`FirebaseAuthErrors.FromPhone`), so `PhoneSignIn` (`AuthException.ErrorOf`) shows "No connection" for a send with no signal, never "Sign-in failed". A network failure anywhere (our time limits, Android's `FirebaseNetworkException`, a request with no answer, a message saying "network"; `FirebaseAuthErrors.IsNetwork`) is `Network`, also for Firebase's step after the Google account picker, which has no Play status code. Phone sign-in checks the app with Play Integrity (the Play Integrity API must be on, `firebase/cloudshell-auth.sh`); on an emulator that always fails with 17028 "Invalid app info in play_integrity_token", so `AddFirebaseAuth` forces the reCAPTCHA check there (`DeviceType.Virtual`), never on a real phone.
- **Packages (in `MobileAppTheme.Firebase`, `PrivateAssets="none"` so their build targets reach the app and process `google-services.json`):** `Plugin.Firebase.Auth` 3.1.1 + `Plugin.Firebase.Auth.Google` 3.1.2 + `Plugin.Firebase.CloudMessaging` 3.1.2 (the **modular** packages — NOT the bundled `Plugin.Firebase`, which drags in Crashlytics and crashes at launch in MAUI). Android **requires** `MainActivity.OnActivityResult` to call `FirebaseAuthSetup.HandleActivityResult(...)`; without it `SignInWithGoogleAsync()` hangs forever (no exception, stuck on "connecting"). `HandleActivityResult` forwards only while a Google sign-in is pending (`GoogleSignInPending`): the photo picker's and dialer's results reach `OnActivityResult` too, and the plugin's handler throws a `NullReferenceException` (shown as `Android.Runtime.JavaProxyThrowable`) that kills the app when nothing is waiting. The app's debug/release **SHA-1 (and SHA-256 for phone auth) must be registered in the Firebase console** and `google-services.json` re-downloaded — otherwise Google sign-in returns `DEVELOPER_ERROR` (status 10) and phone verification fails app-attestation.
- **Android signing ([`docs/android-signing.md`](android-signing.md)):** every build on every PC and in CI is signed with the committed shared dev key `Platforms/Android/Signing/dev.keystore` (alias `androiddebugkey`, password `android`; SHA-1 `A5:F0:C9:…:31:B6` registered in Firebase), so sign-in works everywhere without registering per-machine keys. A Release build switches to the store key only when `ReleaseKeystore` (or env `SIDEGIGPH_KEYSTORE`) points at an existing file. The passwords come from env `SIDEGIGPH_KEYSTORE_PASS` / `SIDEGIGPH_KEY_PASS` and are never in the csproj. Other keystores are git-ignored. CI writes `google-services.json` and the optional store key from secrets (`GOOGLE_SERVICES_JSON_BASE64`, `ANDROID_KEYSTORE_BASE64`, …). Google Play's App signing key needs its own fingerprints in Firebase.
- **Firebase config (not committed; required before an Android/iOS run):** `Platforms/Android/google-services.json`, `Platforms/iOS/GoogleService-Info.plist`, plus a Google OAuth client (Android SHA-1; iOS reversed-client-id URL scheme, which the iOS workflow copies from the plist into `Info.plist` with the Encoded App ID, docs/testflight.md). The app's csproj references the config files with `Condition="Exists(...)"` so the build works without them.

### Switching the auth provider

Nothing outside the adapter project and `MauiProgram` knows the provider is Firebase. To move to another one (Supabase, Azure AD B2C, Auth0, a custom backend…):

1. Create `MobileAppTheme.<Provider>/` next to `MobileAppTheme.Firebase/`: a class implementing `IIdentityProvider` with its `Methods`, mapping every failure to an `AuthError` (log the full exception first), and a `builder.Add<Provider>Auth(...)` extension that does its setup and `Replace`s `IIdentityProvider`. Load the `maui-firebase-auth` skill for the error policy and the `mobile-app-theme` skill for the boundary rules.
2. In `SideGigPh.Maui.csproj`, swap the `MobileAppTheme.Firebase` project reference for the new one; in `MauiProgram`, swap `AddFirebaseAuth(...)` for the new call; in `MainActivity`, remove the `FirebaseAuthSetup.HandleActivityResult` line (or replace it with what the new SDK needs).
3. Remove the Firebase config files and `GoogleWebClientId` if nothing else uses Firebase.
4. Users are keyed by `AuthUser.Uid`; the new provider's ids differ, so existing accounts need a migration (once there are real accounts).

Never call a provider SDK from a page, workspace or service. If the UI needs something the contract lacks (e.g. email sign-in), add it to `IIdentityProvider` / `AuthMethods` / `AuthError` in the skeleton first, then implement it in every adapter.
