# SideGigPh architecture reference

The detail behind the short rules in [`CLAUDE.md`](../CLAUDE.md) → Architecture map. Read the section for the area you are changing, and keep it accurate when the code changes (CLAUDE.md keeps only the rules every session needs).

## Brand (Tarbaho)

Users see the app as **Tarbaho** (how kids say "trabaho"), and so does Android: the package id is
`com.tarbaho.app` (the Android app registered in Firebase, project `sidegigphilippines`). Solution, projects,
namespaces, the Firebase project and Azure names keep SideGigPh. The name shows from `AppTheme.Brand` (top bar,
language and sign-in screens, `BrandMark` on the splash), `ApplicationTitle` in `SideGigPh.Maui.csproj` (launcher
label), the window title in `App.xaml.cs` and the pre-Blazor splash in `wwwroot/index.html`; copy that names the app
says "Tarbaho" in `Copy.cs`.

- **Font:** DM Sans, a round geometric sans close to Airbnb's Cereal, set by `AppTheme.Style.FontFamily` (the
  skeleton's `BrandStyle.FontFamily`, default the phone's own font). The variable-weight Latin file (37 KB) ships
  in `wwwroot/fonts/dm-sans.woff2` with `DM-Sans-OFL.txt`, loaded by an `@font-face` in `app.css`, so the first
  launch offline already has it; characters it lacks (₱) fall back to the phone's font.
- **Taglines:** Pros "Find work near you" / "Umextra para sa Pamilya" (`Copy.RoleProfessionalHint`); Seekers
  "Find ___ nearby" / "May ___ para diyan" (`Copy.SeekerTagline`); before the role is known, `AppTheme.Brand.Tagline`
  says both.
- **Honorifics** (`Services/Honorifics`): workers are Manong, Kuya, Ate or Manang, never "laborers". The name never
  changes, only the honorific: a random one each launch on the `LaunchRouter` splash (both languages, since a first
  launch doesn't know the language yet) and in the search box until a trade is picked; after that the trade's own
  (`Honorifics.For`: Manong for construction (carpentry, masonry and the other building jobs are its jobs); Ate for errands; Kuya for everyday repairs and any
  new trade). Copy takes the word as `{0}`; English lines that want the plural ("Find Kuyas nearby", the empty search
  "No Kuyas…") pass `englishPlural: true` to `AppText.FormatHonorific`. Ate and Manang always stay in the rotation.
- Spell "maghanap" as one word. The logo is a crew of three workers in hard hats with a hammer and a wrench behind them (a team that fixes homes, not one
  person), one single-color path in a 24-unit box (`AppTheme.Logo`), also used by the launcher icon, both splashes and
  the Android notification icon (`ic_notification.xml`). A small nav mark,
  the wordmark font and the final palette are still to come.

## Photos

- **Photos (MVP):** Azure Blob Storage (storage account `sidegigphbfb9`, also the Function App's own storage; container `photos`, blob `{sha256}.jpg`, readable by URL), written only through **`SideGigPh.Api`** (Azure Functions, isolated worker, .NET 10, published to the Function App `SideGigPhApi`, https://sidegigphapi-hrb9bgerbgcgawbm.southeastasia-01.azurewebsites.net/api/). The API checks the user's Firebase ID token, refuses a photo whose header says it is over 64 MP or 16,384px on a side before decoding it (`PhotoImage.IsTooBig`, `413 too-large`; a 48 MP phone photo fits), re-encodes every upload the same way (`PhotoImage`: upright, sRGB, at most 1280px on the long side and never enlarged, progressive JPEG quality 82, EXIF/GPS stripped; screens crop with object-fit cover), hashes the result and refuses a photo another account already stored (anti-fraud rule 2). Photos show straight from their public blob URL, so the container must allow blob-level anonymous read: the API switches a private `photos` container to it on first upload, and fails with a clear message when the account blocks anonymous access (`azure/cloudshell-setup.sh` turns it on; `cloudshell-verify.sh` checks it). **The storage connection string lives only in the Function App's settings (`PhotoStorage`)** or, on a PC, the git-ignored `SideGigPh.Api/local.settings.json`; never in the phone app. Setup and checks: [`azure/`](../azure/README.md). The app reaches it through **`ApiPhotoStore`** (`SideGigPh.Maui/Services/Api/`, registered in `MauiProgram` after `AddMobileAppTheme`, so it replaces the skeleton's `FilePhotoStore`): `POST photos` uploads, `DELETE photos/{id}` removes, each with the user's ID token (`IIdentityProvider.GetIdTokenAsync`). The server's returned id is the photo id; photos show from their public blob URL. The API URL and blob base URL are constants in `MauiProgram` (not secrets).

## Tests

- **Tests:** **`SideGigPh.Tests`** (plain `net10.0`; xUnit 2, FluentAssertions **7.x** (8+ needs a paid licence for commercial use), `Microsoft.AspNetCore.TestHost`, coverlet). `Unit/` (by feature, fakes in `TestSupport/`, no network or database) and `Integration/` (the real `SideGigPh.Api` functions served in memory at the routes in their `[HttpTrigger]`s, the real stores on a fresh SQL Server database built like live is upgraded (`Sql/001-schema.sql`, then every `NNN-schema-*.sql` in order, then `004-config.sql`; `SchemaScriptTests` re-runs them to prove the guards), the real `FirebaseTokenValidator` with a test signing key, photos in an in-memory blob container, and per test person the app's real services and `AddSideGigPhApi` adapters; trait `Category=Integration`, skipped with a reason when no SQL Server: LocalDB on Windows or `SIDEGIGPH_TEST_SQL`). The app targets only Android/iOS, so the csproj **compiles `SideGigPh.Maui/Models/**` and `Services/**` (plus the `*Routes.cs`) into the tests by link**: keep pages' rules in `Services/` (pages aren't compiled there). Two test seams, unused by the app: `ApiOptions.Handler` (an `HttpMessageHandler` for `ApiClient`) and `FirebaseTokenValidator`'s optional `signingKeys`. Snapshot tests in `Unit/UpdateSafety/` fail on purpose when an id, JSON field name or error code changes. Coverage of the core code is ~100% (`coverage.runsettings`). How to run and what each folder protects: [`SideGigPh.Tests/README.md`](../SideGigPh.Tests/README.md); after a relevant change load the `run-tests` skill

## Key Ports (Interfaces)

**`IIdentityProvider`** (skeleton, `MobileAppTheme/Auth/`) — Auth abstraction; Firebase is one swappable adapter (see Auth → Switching the auth provider)
- `Methods` (which `AuthMethods` the provider supports)
- `SignUpWithPhoneAsync(string phoneNumber)` (sends the SMS code, for sign-in or linking)
- `VerifyPhoneOtpAsync(string verificationId, string userEnteredCode)`
- `LinkPhoneAsync(string verificationId, string userEnteredCode)` (adds a verified number to the signed-in account, same uid; `AuthError.PhoneInUse` if another account has it)
- `SignInWithGoogleAsync()`, `SetDisplayNameAsync(string)`
- `GetCurrentUserAsync()`, `GetIdTokenAsync()` (the ID token for our own API as a Bearer header), `SignOutAsync()`
- **A dead session is signed out:** when the token refresh says the account is gone (deleted in the console or by Delete account elsewhere, disabled, revoked), `GetIdTokenAsync` signs out (`FirebaseIdentityProvider.IsDeadSession`; on Android the native `FirebaseAuthInvalidUserException` arrives unwrapped, so the type name is checked down the inner exceptions). Before this, such a phone stayed "signed in", every call went out without a token (401), screens showed empty and its error reports could not be sent either.
- **Nothing waits on the provider forever:** the Firebase adapter gives sending the SMS code `SendCodeLimit` (90 s, then a `TimeoutException` that `PhoneSignIn` shows as `AuthError.Network`) and the ID token `TokenLimit` (15 s, then logged as an error and the call goes out without one), because every API call waits for the token. The end of either interview waits for its saves at most `OnboardingFinish.WaitLimit` (15 s, `Services/OnboardingFinish`), and not when they failed, then opens the app anyway (the answers are on the phone and home loads its own data); both cases are logged, so they reach the error reports. The setup and Publish load only what is on the phone (`ProWorkspace.EnsureDraftLoadedAsync`, no network call), so they show at once on a slow connection; Pro home's `EnsureLoadedAsync` adds the chats and reviews. A session Firebase says is dead (`UserTokenExpired`, `UserNotFound`, `UserDisabled` while getting the token) is signed out, so the next screen asks to sign in instead of every call failing.

> **Naming:** user-facing text (`Copy`, `ReferenceData`, brand tagline) always says **"Skilled Worker"** / "skilled worker" (Taglish too), never "pro", "Professional" or "tradesman". Code keeps **"Professional"** (`ProWorkspace`, `ProfessionalListing`, `/professional` routes, `Professionals` table) for the side-gig service provider (aircon tech, plumber — and also non-trade pros like web developers or video editors), never "tradesman".

**`IOnboardingStore`**: the onboarding answers, saved on the device with no account (`Local/FileOnboardingStore`). It writes one JSON file in `FileSystem.AppDataDirectory`, using a source-generated serializer and an atomic write. There is no SQLite yet; add it when local data needs querying. Don't use the WebView's `localStorage`. **Android backup is off** (`android:allowBackup="false"`): Auto Backup restored an uninstalled build's answers and Firebase session onto a fresh install, which skipped the sign-in after the language with a session that then failed; an uninstall must mean a fresh start (the account's data is on the server).

**`IContactLauncher`** (skeleton): Call / Text a pro through the phone's apps (`MobileAppTheme/Services/Local/DeviceContactLauncher`, MAUI `PhoneDialer` / `Sms`). Android needs the `tel` / `smsto` `<queries>` in `AndroidManifest.xml`.

**`IChatRepository`** (`Api/ApiChatRepository`): **in-app chat**, one `Chat` per Seeker and pro (id `{proId}_{seekerId}`, carrying both names, the job from the Seeker's answers and the `LastMessage`) with its `ChatMessage`s (`Text`, or `Call` when the Seeker's Call button opened the dialer). `GetInboxAsync(personId, ChatSide, beforeChatId)` is one page of each side's Inbox, `Paging.Inbox` (30) chats, newest first (`GET chats?side=…&take=30&before={chatId}`; without `take` the server sends every chat, for app versions before paging): the workspace keeps the pages it loaded (`InboxPages`: a refresh re-reads the first page and keeps older pages below it; `ProWorkspace.HasMoreChats` / `MoreChatsAsync`, `SeekerWorkspace.HasMoreThreads` / `MoreThreadsAsync`) and both Inbox pages load the next one with `LoadMoreOnScroll` at the end; the badge counts the loaded chats; unread = the other person wrote last after this side's read time (`MarkReadAsync`); `GetMessagesAsync(chatId, beforeMessageId)` reads one page, `Paging.Messages` (20) per page (`GET chats/{id}/messages?take=20&before={messageId}`; without `take` the server sends every message, for app versions before paging): a chat page opens on the newest page, scrolled to the bottom, and loads the page before its oldest message when the person scrolls to the top (swipes down) (skeleton `LoadMoreOnScroll` `Edge="LoadMoreEdge.Top"`, which keeps the reader's place); the loaded messages live in **`ChatHistory`** (`Services/`: `FromLatest`, `WithOlder`, `WithLatest`, `With`; each workspace's `GetMessagesAsync` / `OlderMessagesAsync` / `NewMessagesAsync`). `Watch(chatId, lastMessageId, …)` gives live updates while a chat is open: it polls `GET chats/{id}` every `ApiChatRepository.WatchInterval` (5 s), skipped while the app is hidden (skeleton `AppVisibility`, set by `App`'s window `Stopped`/`Resumed`), and hands back the chat when its last message differs from the one the page shows; the page passes it to the workspace's `ChatChanged` and adds the newest page under what it shows (`NewMessagesAsync`). Only the Seeker can start a chat; the server stamps message times and takes the worker's name from their listing. **`IUserRepository`** (`Api/ApiUserRepository`, `users/me`): the signed-in person's `UserProfile` (account name/number, language, side (the earnings goal is no longer asked: the app sends `IncomeGoalId` null), and `ProfilePhotoId`: the account's one profile photo, the Seeker's own or the worker's listing photo, unique across accounts by `UX_Users_ProfilePhoto`), saved by `LocalAccount.SaveProfileAsync` at the role pick, the end of either interview, a language change and a profile-photo change; `SaveDeviceAsync(token, platform)` (`PUT users/me/devices`) registers this phone for notifications. **`IReviewRepository`** (`Api/ApiReviewRepository`): Seekers write one review per pro they chatted with, **only 24 hours after the chat started** (`ReviewRules.WaitAfterChatStarts` in `SideGigPh.Contracts`, shared by both sides; `SeekerWorkspace.CanRate` hides the Rate buttons and `ToRate` until then, and the thread shows `Copy.RateLater`; an earlier review can always be changed) (`SaveAsync` replaces; the server answers `403 no-chat` without a chat and `403 review-too-soon` before then); stars for ranking travel on each listing (`ProfessionalListing.Reviews`, averaged by SQL in the search query). Reviews about a pro survive their Start over.

**New-message notifications** (not SignalR: it only reaches an open app, which already polls): **`IPushNotifications`** (skeleton port, default `NoPushNotifications`; adapter `FirebasePushNotifications` in `MobileAppTheme.Firebase`, added by `builder.AddFirebasePush(channels)` in `MauiProgram` with the two Android channels `PushData.CustomersChannel` (loud) and `RepliesChannel` (quiet)). The server decides how loud: **a customer writing to a Skilled Worker rings** (title "New customer: …" on the first message); **a worker answering a Seeker only puts a red dot on the app icon** (Android: a silent tray line on the low-importance channel; iOS: badge only). One notification per chat (tag / `apns-collapse-id` = chat id), badge = the receiver's unread chats, data `PushData.ChatId` / `ProfessionalId` / `Side`, nothing shown while the app is open (it refreshes the Inbox instead). **`ChatAlerts`** (`Services/`, singleton) is the app side: `ProLayout` / `SeekerLayout` `Attach` it (Inbox refresh on arrival, open the chat on a tap, `ChatAlerts.PathFor`), call `ShowUnread(Workspace.UnreadChatIds)` on every change (read chats leave the tray, the badge follows), and register the phone; the permission is asked only with a reason (`AskAsync`: Pro home opening with a live listing, the Seeker's `ThreadPage` after a send), never at first launch. Android needs `POST_NOTIFICATIONS`, `MainActivity` `LaunchMode.SingleTop`, and the `ic_notification` drawable (the logo path, white) named in the manifest. Server: `ChatFunctions.Send` → `ChatNotifier` (wording, English/Taglish from `Users.Language`) → `IPushSender` (`FcmPushSender`, Firebase Admin SDK, setting `FirebaseServiceAccount`; `NoPushSender` without it); a retried message id or a failed send never notifies twice or fails the message; dead tokens are deleted. Setup: [`firebase/README.md`](../firebase/README.md) → Notifications.

**`JsonFile<T>`** (skeleton, `MobileAppTheme/Services/Local/`): the one place that reads/writes an app-private JSON file (atomic temp-file write, corrupt file reads as missing, source-generated `JsonTypeInfo`). `FileOnboardingStore` and `FileConfigCache<T>` (the app config) use it.

**`LocalAccount`** (`Services/`, singleton, also registered as the skeleton's **`IAppAccount`** that `MePage` uses): the person on this phone, whichever side: app language (`SetLanguageAsync`, raises `Changed` for the layouts) and **Start over** (`StartOverAsync`): deletes their photos, published listing, chats, reviews and profile (`DeleteForPersonAsync` on the chat and review repositories, `IUserRepository.DeleteAsync`), clears `IOnboardingStore` (`ClearAsync`) and makes both workspaces `Forget()`, so `/` restarts onboarding at the language screen. **Sign out** (`SignOutAsync`) signs out of the provider and makes both workspaces `Forget()` but keeps the answers on the phone; the skeleton's `AddPhonePage` offers it as "Sign in with this number" when linking fails with `AuthError.PhoneInUse` (a Google account whose number belongs to another account, often the person's own earlier phone sign-in), which before was a dead end since nothing in the app signed out. Delete account is `DeleteAccountAsync`.

**Ids:** the signed-in person's uid is their id on both sides (the server always takes it from the token, never the body): `ProWorkspace.MyId` (also the listing id, `Professionals.Id`) and `SeekerWorkspace.MyId`, both set when the workspace loads. Pages compare against those, never a literal. Only when no sign-in provider is registered do they fall back to the old fixed ids `ListingMapper.OwnListingId` (`"own"`) and `SeekerWorkspace.LocalSeekerId` (`"me"`).

**API adapters** (`SideGigPh.Maui/Services/Api/`, the only app code that talks HTTP): `ApiClient` (one `HttpClient`, the Firebase ID token on every request, `ApiOptions(ApiUrl, PhotoBaseUrl)`; its optional `Handler` is for tests only), `ApiProfessionalProfileRepository`, `ApiUserRepository`, `ApiReviewRepository`, `ApiChatRepository`, `ApiConfigRepository`, `ApiPhotoStore`, and `ApiMapping` (contracts ↔ `Models/`; models never get contract types). `AddSideGigPhApi(options)` registers them all in `MauiProgram`, after `AddMobileAppTheme`. Reads that fail (offline, server error) are logged and come back empty (`ApiClient.ReadAsync`); writes log and throw (`EnsureWritten`), and the pages already show a "didn't send / didn't publish" message. A listing sends photos by id (read from their blob URLs); the server stores ids and builds URLs.

**Round trips and caching** (each window is a named constant): `ApiProfessionalProfileRepository` keeps each page of search results for `SearchFreshFor` (60 s, per query and page: the server ranks, so a changed town, budget or job is a new request) and a listing for `ListingFreshFor` (5 min, filled by searches too; the Inbox and profile reuse it), both in `TimedCache<T>` (successful reads only); its publish/remove drops them. Each workspace's `RefreshActivityAsync` reads its lists side by side; tab pages call `RefreshIfStaleAsync` (skips within `ActivityFreshFor`, 15 s). The app's `HttpClient` asks for gzip (`ApiClient.GzipHandler`) and the API gzips JSON answers of 860 bytes or more (`GzipMiddleware`, which wraps the function's `ObjectResult`, because the Functions host writes the result after the middleware returns; 204/304 and callers that don't ask are untouched). Writes never re-read everything: a send, reply or mark-read updates the list from the server's answer (`Put`), and the chat page appends the saved message. Server side, `ListingCache` (`SideGigPh.AzureSQL`, `IMemoryCache`) keeps a trade's listings 30 s per instance (the next pages of a search rank that same list again) and is cleared by a publish, removal or review on that instance.

**Server** (`SideGigPh.Api` + `SideGigPh.AzureSQL`): one function class per area (`UserFunctions`, `ProfessionalFunctions`, `ReviewFunctions`, `ChatFunctions`, `PhotoFunctions`, `ConfigFunctions`, `ErrorReportFunctions`), each checking the token first (`FirebaseTokenValidator.GetUidAsync` / `GetCallerAsync`, which also gives the verified `phone_number`) (the one public route is `GET config`, reference data read before the account is ready; `ApiWiringTests.PublicRoutes`), then calling a store (`UserStore`, `ProfessionalStore`, `ReviewStore`, `ChatStore`, `PushDeviceStore`, `ConfigStore`, `OtherJobNoteStore`, `ErrorReportStore`) that holds the data rules and answers with contracts or an outcome enum. Errors answer `{ "error", "detail" }`: `ErrorDetailsMiddleware` turns any exception into `500 exception` (or `400 bad-body`) with the stack trace in `detail` while `ApiResults.ShowDetails` is on (MVP debugging; on unless the Function App setting `ShowErrorDetails` is `false`: set that before launch), and the app logs the whole answer (`ApiClient.EnsureWrittenAsync`). Multi-row writes use `db.InTransactionAsync` (retry-safe on Azure SQL); a caller's own data sits under `…/me` / `…/mine` routes. Writes a script could repeat are limited per account by **`CallerLimits`** (in memory per instance, sliding window; `Limited`: chat messages 30/min, new chats 20/h, "Others" notes 20/h, error report batches 12/h, photo uploads 10 per 15 min, reviews 30/h): past it `429 too-many-requests` (`ApiErrors.TooManyRequests`), which the app shows as its usual didn't-send message. Search ids that can't be a trade or area find nobody without a database read or cache entry. "Others" (`OtherWork.TradeId` `other`, and each trade's `…-other` job) is accepted as a listing's and a job post's trade and job; search takes the Seeker's typed `otherText` and `SearchRanker.OtherWordsMatch` puts workers whose `ListingDto.OtherWork` shares its words first (the job-post feed still orders "Others" posts by distance only). Settings: `PhotoStorage`, `SqlDatabase`, `FirebaseProjectId`, `FirebaseServiceAccount` (notifications; optional), `ShowErrorDetails` (optional).

**Error reports** (`Services/Diagnostics/`, so we can fix what we can't reproduce, like a phone that hangs after the interview's Done): **`ErrorLog`** (singleton) keeps the problems the app had on this phone in `diagnostics.json` (port **`IErrorLogStore`**, `Local/FileErrorLogStore`, kept by Start over): errors any code logs (**`ErrorLogLoggerProvider`**, an `ILoggerProvider` service; the app's own information and warnings become trail lines), crashes and unobserved task errors (**`ErrorReporting.Start`**, from `App`; a crash saves the log before the app closes), on Android what .NET never sees (**`Platforms/Android/AndroidCrashCapture`**, from `MainApplication.OnCreate`: a Java exception nothing caught, source `Crash.Java`; and at each launch how earlier runs ended, read from `ApplicationExitInfo` on Android 11+ and turned into reports by **`PastExits`**, source `Crash.LastRun`: crash, native crash (WebView, drivers), ANR with the dump's `"main"` thread, a memory kill while on screen; dated when it happened, without this run's screen, each exit once via the `diagnostics.lastExitSeen` preference), and a loading screen up longer than the skeleton's `BusyIndicator.StuckAfter` (20 s: its `Stuck` event, raised even if the wait never ends; `Unstuck` adds the whole wait to the trail). Each report carries the screen (`Components/Shared/ScreenTrail` in `Routes.razor` tells it every path, never the query) and the last 15 screens and steps; the same problem repeated only counts up; at most 50 reports for 14 days. **Every text is scrubbed when recorded** (`ErrorReportRules.Scrub` in `SideGigPh.Contracts`: sign-in tokens, phone numbers, emails, Firebase uids also inside chat ids, photo hashes, query strings) and again by the server. **`ErrorReportSender`** sends batches of 20 (`IErrorReportRepository` → `Api/ApiErrorReportRepository` → `POST error-reports` → `ErrorReportStore` → `ErrorReports`) 30 s after launch, then every 10 min while the app is on screen, only while someone is signed in (what happened before sign-in waits); a failed send waits for the next try, a batch the server refuses as bad is dropped, and neither logs an error (that would report itself). Batches carry a random install id, the app version, the **code version** (the git commit, stamped by the csproj's `StampCodeVersion` target; `-dirty` = built with uncommitted changes) and the **channel** (`AppChannel`: `dev` for Debug, `beta` for Release, `prod` with `-p:AppChannel=prod`; read by `MauiProgram.BuildInfo`), the OS version and phone model, never the account. **Privacy:** on by default (legitimate interest: keeping the app working), said in the privacy policy (what is sent, never messages, names or numbers, kept 90 days), and the Me page's **`ErrorReportsSwitch`** (both sides) turns it off, which deletes what waits. Declare "Crash logs" and "Diagnostics" in Google Play's Data safety form and "Diagnostics" in Apple's privacy label. Read them in the portal Query editor (`docs/data-model.md` → `ErrorReports`).

**`IDeviceLocation`** (skeleton `Local/DeviceLocation`, MAUI `Geolocation` with `GeolocationAccuracy.Best`, 15 s):
`GetCurrentAsync` asks for `Permissions.LocationWhenInUse` only when called, never throws, and answers a `LocationFix`
(`Found` + `GeoPoint` + accuracy in metres, `Denied`, `Off`, `Failed`); `OpenAppSettings()`. Android declares
`ACCESS_FINE_LOCATION` and `ACCESS_COARSE_LOCATION` (location hardware not required), iOS
`NSLocationWhenInUseUsageDescription`; **never background location**. The app's rules are `Services/WorkArea`
(`Read`: only a point in the Philippines box the server takes and within `RoughAfterMeters`, 1 km, is used, so a
phone allowed only "approximate location" gets `Rough` and a message; `RadiusChoices` 3/5/10/20/30/50 km). The one
place the permission is asked is the app-generic `Components/Shared/LocationButton` ("Use my location": set or "we
use the middle of your town", the reason under it, a message per failure, Open Settings after a refusal), on
the worker's **Where you work** page (`ProRoutes.WorkArea`, `WorkAreaPage`, from Me: base point and travel distance
chips; Save → `ProWorkspace.SetWorkAreaAsync`, kept in `ProfessionalDraft.BaseLatitude` / `BaseLongitude` /
`RadiusKm`, sent with every publish as `ProfessionalListing.BasePoint` / `RadiusKm`, a live listing re-published like
any edit) and on the household's post form (`NewPostPage`). Nothing waits on location: without a point the server
uses the towns' centres. A map pin for when location is refused or rough is not built yet (it needs a Google Maps key
for Android).

**`IPhotoPicker`** (skeleton `Local/DevicePhotoPicker`, MAUI `MediaPicker.PickPhotosAsync`, resized to 1280px; `PickAsync` returns a `PhotoPick` whose `PhotoPickStatus` is `Picked`, `Cancelled`, `PermissionDenied` or `Failed`, and `OpenAppSettings()` opens the app in Settings) and **`IPhotoStore`** (skeleton default `Local/FilePhotoStore`; SideGigPh uses `Services/Api/ApiPhotoStore`, see Photos above): photo id = SHA-256 of the bytes (anti-fraud rule 2). `FilePhotoStore` keeps files in `AppDataDirectory/photos` shown as data URLs; `ApiPhotoStore` shows https blob URLs. `SaveAsync` throws `PhotoStoreException` when the upload fails (`Taken` = another account has this photo, the API's `409`). `ProWorkspace` turns pick and upload outcomes into a `PhotoAddResult.Problem` (`CouldNotOpen`, `NoPermission`, `UploadFailed`, `Taken`) and `PhotoAddNotice` shows a different message for each (no permission adds an Open Settings link); `DeleteAsync` logs a failure and carries on. Gallery-only, no camera, so Android 13+ and iOS (system photo picker) need no permission; on Android 12 and older `DevicePhotoPicker` checks and asks for `Permissions.StorageRead` first (the manifest has `READ_EXTERNAL_STORAGE` `maxSdkVersion=32`; iOS has `NSPhotoLibraryUsageDescription`). On Android the app's `ILogger` output also goes to logcat (`Platforms/Android/LogcatLoggerProvider`, Information and up, with full exceptions): `adb logcat -s SideGigPh`.

**`IProfessionalProfileRepository`** (`Api/ApiProfessionalProfileRepository`): `SearchAsync(query, skip)` (`GET search/professionals?categoryId=…&areaId=…&serviceId=…&cityId=…&budgetId=…&skip=…&take=4`: one page of results **ranked on the server**, a `SearchPageDto` with both groups' totals; the old unranked `GET professionals?categoryId=…&areaId=…` stays for app versions before paging), `GetByIdAsync` serves the public profile and Inbox, `PublishAsync(listing)` (`PUT professionals/me`) (anti-fraud rule 1: the listing number is the token's verified `phone_number`, unique in `Professionals`; the account holding it now wins, so a stale account's listing with it comes down and its profile loses the number, and `PublishResult.PhoneTaken` is only a race; no verified phone = `403 phone-required`), `RemoveAsync` takes the caller's listing out of search (Start over), `GetOwnDraftAsync(uid)` reads the caller's own live listing fresh (`GET professionals/{uid}`, photo ids included) as a `ProfessionalDraft` for **`ListingRestore`**: a worker whose app was reinstalled (or who signs in on a new phone) gets their live listing back. `LaunchRouter` calls it once signed in, only while the phone holds no answers: no side picked, or the worker side picked with nothing answered yet (the role page's "Sign in with this number" lands here before the first question); nothing on the phone is ever overwritten, so they open Pro home instead of the interview; no listing, a Seeker or a failed read (logged) leaves the role question as before.

**App config** (data every page needs that may be hours stale: the trades and jobs with their price guides, towns, the minimum wage, the old price tiers, experience, urgency, income goals; one `AppConfig` model, one `ConfigDto`): loaded **once per launch, behind the splash** (`LaunchRouter` awaits `AppConfigService.LoadAsync()` before anything else), then held in memory by `ReferenceData` (`UseConfig`, guarded by `CanUse`: no empty list, every trade has jobs, the ids the code names exist). Pages never fetch it. The rules are the skeleton's generic **`RemoteConfig<T>`** (`MobileAppTheme/Services/RemoteConfig.cs`): the phone's copy (`config.json`, skeleton `FileConfigCache<T>` over `JsonFile<T>`, a `Stamped<T>` with `SavedAt` and the server's `Version`) is used with **no network call for 12 h** (`RemoteConfigRules.FreshFor`), but only by the app build that saved it (`Stamped.AppBuild` = `RemoteConfigRules.AppBuild`, version + commit from `BuildInfo`): an update or reinstall asks the server at its first launch, so it never runs on the trade list the old build saved; after that the app asks `GET config` with `If-None-Match: <saved ETag>` (`ApiClient.GetIfChangedAsync`, no token) and the server answers **`304` with no body** when nothing changed (the copy counts as checked again) or `200` with the new config (saved); offline or slower than 8 s (`FetchTimeout`) it uses the stale copy, and with none it runs on `BuiltInConfig`. A server config that isn't usable is never used or saved. Server side `ConfigStore` keeps the config and its ETag (SHA-256 of the JSON) **12 h per instance** (`ConfigFor`; restart the Function App to apply a `004-config.sql` edit sooner, so an edit can take up to ~24 h to reach every phone) and `ConfigFunctions` sets `ETag` and `Cache-Control: public, max-age=43200`. **Why a JSON file and not SQLite:** it's one small document always read whole at launch; `JsonFile<T>` writes atomically (temp file, then move) and a corrupt file reads as missing, so the worst case is the built-in copy. Add SQLite only when local data needs querying. Ports: `IConfigSource<AppConfig>` and **`IOtherJobNoteRepository`** (both `Api/ApiConfigRepository`: `GET config`, `POST other-jobs`); **`OtherJobNotes`** (`Services/`, singleton) sends the typed "Others" text trimmed and cut to `MaxText` (= the server's `OtherJobNoteStore.MaxNote`), failures only logged. New stale-OK data goes into this same config (a `ConfigOptions` list or a new `ConfigDto` field), not a new endpoint.

**Launch town and barangays** (the narrower launch: critical mass in Angono, then one barangay at a time, before spreading). Both are server data in `004-config.sql`, so changing them is a SQL-only edit: the default town is the one row of the `ConfigOptions` list `default-town` (its `Id` names the town; `ConfigStore` sends it as `ConfigDto.DefaultTownId` only when it is a served town), the barangays are `dbo.Barangays` (`021-schema-barangays.sql`; `ConfigDto.Barangays`, `BarangayDto` with its `TownId`). The app holds them in `AppConfig.DefaultTownId` / `BarangaysByTown` (null in a copy saved before them, so nothing breaks) and reads them through `ReferenceData.DefaultTownId`, `BarangaysOf(cityId)`, `FindBarangay(cityId, id)`; `BuiltInConfig` carries Angono and all 31 barangays. **The default only pre-selects, it never locks:** the Seeker's town question shows it picked (`SeekerAnswers.TownShown()`, also the search request and Seeker home's town filter when they have no town), the worker's towns question starts with it ticked (`ProfessionalDraft.PreselectDefaultTown`, only when no town is ticked), the post form starts on it; Taytay and Antipolo stay selectable. **A barangay is never required:** the app-generic `Components/Shared/BarangayField` (a `MudSelect` that starts on "Not sure / skip", nothing for a town without a list) sits on the Seeker's town question (a town with barangays waits for Next instead of moving on when tapped; `SeekerAnswers.BarangayId`, `PickBarangay`) and on the post form (`JobPostDraft.BarangayId`, filled from the household's barangay, remembered from a post in their home town by `RememberPost`). Picking another town drops a barangay of the old one (`PickTown`). The server keeps a post's barangay only when it is one of that town's (`JobPostStore.ServedBarangay`, else NULL, never a refusal) and sends it as `JobPostDto.BarangayId`; workers see "Angono · Brgy. San Isidro · 3 km away" (`TownText.Place`), the household's point stays private. A saved barangay that was retired or isn't in the household's town is dropped on load (`OnboardingCleanup.DropUnservedBarangays`), and nothing is asked again. Search and the feed don't rank by barangay yet.

## Versioning

- **One source:** `Directory.Build.props` at the repo root. `AppVersionNumber` is SemVer `major.minor.patch` (now
  `0.1.0`), `AppVersionStage` the pre-release stage (empty since the Play Store launch; `rc` for a pre-release), and
  `BuildNumber` comes from CI (`-p:BuildNumber=${{ github.run_number }}`; `0` on a PC). Together they make
  `AppVersionLabel`: `0.1.0-rc.12` from CI, `0.1.0-rc` on a PC, `0.1.0` for a final release. To ship a new version,
  change the two properties there and commit; nothing else holds a version.
- **Where it goes:** the app's csproj maps it to the store fields (Android `versionName` = the whole label and
  `versionCode` = the build number; iOS `CFBundleShortVersionString` = the three numbers, since Apple allows nothing
  else, and `CFBundleVersion` = the build number). `Directory.Build.targets` (`StampBuildInfo`, on for the app and the
  API) writes the label, the git commit (`git describe`, `-dirty` with local changes) and the app's channel into the
  assembly as `[AssemblyMetadata]`.
- **App:** `Services/Diagnostics/BuildInfo` (`BuildInfo.Current`) reads the stamp. `AppTheme.Brand` passes
  `BuildInfo.Current.Label` (`v0.1.0-rc.12`) as `AppBrand.Version`, which the skeleton shows as a muted caption under
  the spinner of `SplashScreen` (the launch splash and the busy splash) and beside the logo in `AppTopBar`. The
  pre-Blazor splash in `wwwroot/index.html` is static HTML and shows no version; it is on screen for a moment only.
- **Error reports** carry `AppVersion` = `0.1.0-rc.12 (12)` (label + store build), `CodeVersion` and `Channel`
  (`DeviceStamp`, unchanged columns).
- **API errors name both builds.** `ApiClient` sends `X-App-Version: 0.1.0-rc.12 (beta; 48466c9)` on every call
  (`ApiOptions.ClientVersion`, header names in `Contracts.ApiHeaders`). The server's `ErrorDetailsMiddleware` puts
  `X-Api-Version` (`ApiVersion.Current`, e.g. `0.1.0-rc.57+48466c9`) on every answer, logs every crash with the
  caller's app version, and logs a warning for every refusal a function answers (400, 403, 409, 429, 5xx; not the
  everyday 401 and 404). On the phone a failed call is logged as `API 0.1.0-rc.57+48466c9: couldn't … : 500 …`, and
  that log line becomes an error report, so one row in `ErrorReports` says which app build met which API build.
- **The app and the API count builds separately** (each workflow's own run number), because they ship separately.
- **A PC build over a CI build:** Android refuses to install a lower `versionCode` over a higher one, so a tester's
  phone with a CI build needs that build uninstalled before a Visual Studio build goes on it.

- **Before turning analytics on for testers:** add it to the privacy policy (`docs/legal/privacy-policy.md`) and the
  stores' data forms; the Me page has no analytics switch yet (`IAnalytics.SetEnabled` is there for one).

## Feedback board

- **What:** both sides open it from the Me page (`SeekerRoutes.Feedback` / `ProRoutes.Feedback` →
  `/feedback/{side}`, `Components/Feedback/FeedbackPage`, full screen): suggestions with a vote button, **most voted
  first** (open and planned ones, then finished ones), in pages of `Paging.Feedback` (20). The board shows no names.
- **Suggesting (`SuggestPage`, `/feedback/{side}/new`):** write a title (6–100 characters) and optional details →
  the app asks `GET feedback/similar?q=…` → when look-alikes exist, **"Is it one of these?"** lists them
  (`SimilarSuggestion`): "Yes, same idea" adds the person's vote to that one and posts nothing; "No, mine is
  different" posts it. With no look-alike it posts at once. The writer's own vote is the first.
- **Look-alikes (`SideGigPh.AzureSQL/FeedbackMatch`):** titles are compared by the words that carry meaning (small
  English and Tagalog words and wish-list words like "add", "sana", "po" dropped, plural "s" ignored); two are
  similar when at least half of the shorter one's words are in the other (`MinScore`). The server compares against
  the 500 most voted (`FeedbackStore.MaxCompared`). No AI: the person confirms the match.
- **Rules (server, `FeedbackStore`):** one vote per person (`PK_FeedbackVotes`; voting twice changes nothing);
  `Votes` is recounted from the vote rows on every change; the same title from the same person again answers with
  the first; the writer may delete their own only while nobody else voted; a report adds a row to `Reports`
  (`SubjectId` `feedback:{id}`); `declined` and `hidden` leave the board. Limits: 10 suggestions and 120 votes an
  hour per account. **Delete account** removes the person's votes (counts follow) and clears `AuthorUid` on their
  suggestions, which stay.
- **App (`Services/FeedbackBoard`, singleton, port `IFeedbackRepository`, adapter `ApiFeedbackRepository`):** holds
  the loaded pages; a vote shows at once and is put back if it didn't reach the server; a new suggestion goes on top
  of the list; the order otherwise stays put while on screen and is re-sorted on the next load.
- **Operator:** `UPDATE dbo.FeedbackPosts SET Status = 'planned' WHERE Id = …` (or `done`, `declined`, `hidden`);
  top of the board: `SELECT Id, Votes, Status, Side, Title FROM dbo.FeedbackPosts ORDER BY Votes DESC`.

## Job posts

- **What:** a household says once what it needs done and what it is ready to pay, and the workers of that trade
  nearby see it. Tarbaho stays a directory: the budget is the household's own number, nothing is paid in the app.
- **Seeker side:** the **Post** tab (`SeekerRoutes.Posts` = `JobPostRoutes.Mine`, `Components/JobPosts/MyPostsPage`,
  inside `SeekerLayout`) lists their posts, newest first, each saying whether workers can still see it, with
  "Take down" on the open ones. "Post what you need" opens `NewPostPage` (`/posts/new`, full screen): kind of work,
  the exact service, town (all three start from their last search), the problem in their words (10–600 letters),
  their budget in pesos and up to 3 photos, uploaded as they are picked (`JobBoard.AddPhotosAsync`).
- **Pro side:** the **Requests** tab (`ProRoutes.Requests` = `JobPostRoutes.Feed`, `ProPostsPage`, inside
  `ProLayout`) is the feed, a page of `Paging.JobPosts` (10) at a time with `LoadMoreOnScroll`. Until the listing is
  published it says to publish first: the server matches posts to the published listing (trade, services, base
  point, `RadiusKm`), not to the draft on the phone.
- **Relevance (`JobPostStore.FeedAsync`, one SQL query):** open posts whose trade is the worker's, within the
  worker's own `RadiusKm` of their base point (`Professionals.Location.STDistance(JobPosts.Location)`, metres, both
  on spatial indexes; when either point is unknown, posts in a town the worker goes to). Never the worker's own
  posts, nor those of someone blocked either way. Order: **a service the worker offers first, then nearest, then
  newest.**
- **Privacy:** a post's point is the phone's when the household tapped **Use my location** on the form
  (`LocationButton`, `JobPostDraft.Point`), else the centre of its town (`GeoRules.CentreOf`). The point never leaves the server: a worker
  gets the town and `distanceKm`, whole kilometres and never under 1 (`JobPostStore.DistanceKm`), so a place can't
  be worked out from it.
- **Abuse:** posts are limited to 10 an hour per account (`Limited.JobPost`); the same post sent twice is one post;
  the flag on a card sends it to the operator's `Reports` queue (`job-post:{id}`) and takes it off that worker's
  feed; the operator hides it with `UPDATE dbo.JobPosts SET Status = 'hidden' WHERE Id = …`. Delete account removes
  a household's posts and their photos, and a worker's offers. Offers are limited to 60 writes an hour
  (`Limited.JobOffer`).
- **App (`Services/JobBoard`, singleton, port `IJobPostRepository`, adapter `ApiJobPostRepository`):** both lists
  and their actions; a failed call never throws into a page. `JobPostCard` draws a household's own post (Post tab).
- **A worker's requests are short rows** (Airbnb Trips style, `Components/JobPosts/RequestRow`, the Requests feed,
  My offers and Pro home's "Newest near you", divider between rows): a small `PostThumb` (the customer's first photo,
  else the service's own picture, `AppImages.For(serviceId)`), the service with the budget right-aligned in money
  green, the place · distance, then time · state ("You offered ₱1,000", "Picked you", "Not picked") and one button
  look, "Offer" or "My offer". No trade chip, no description, no flag on the row: the whole row opens the request's
  own page. The rules are `Services/RequestItem` (`RequestState` New / Offered / Picked / NotPicked, built from a
  feed post or a `MyOffer`; `Offered` / `Withdrawn` after the worker's writes) and `Services/Localization/RequestText`
  (each line's words), tested in `Unit/JobPosts/RequestRowsTests`. The Requests tab's title has no explainer line,
  and a 2-way switch (`RequestsSwitch`, `MudToggleGroup`) moves between **New** (`ProPostsPage`) and **My offers**
  (`MyOffersPage`).
- **A request's own page** (`RequestDetailPage`, `ProRoutes.Request(id)` = `JobPostRoutes.Request(id)` =
  `/professional/requests/{id}`), modelled on Airbnb's **"Review and continue"** booking screen
  (`docs/ux/airbnb-2026-11-18/airbnb-20…22`). **Full screen, outside `ProLayout`** (no top bar or tabs, so the button
  has room; it calls `ProWorkspace.EnsureLoadedAsync` itself, `/` when that fails): ✕ (back to Requests) and 🚩 in a
  `SheetHeader`, a big left title that says what to do or what became of it (`RequestText.RequestPageTitle`: "Send your
  price", "Your offer", "Picked you", "Not picked"), then **one outlined card**: `RequestSummary` (the customer's first
  photo, else the service's picture, as a `PostThumb`; service; place · distance; ★ stars when `HouseholdStars` · how
  long ago, `RequestMeta`) and `DetailRow`s split by dividers (bold label, value, one muted line, an optional gray
  button on the right): **Your price** (once offered: green price, "Waiting for the customer" and the note,
  `RequestOfferDetail`, with **Change**), **Their budget** (green), **What they need** (the customer's words and the
  photo strip). A new request then asks **Your price** as two radios in one card (`PriceChoice`, Airbnb's "Choose when
  to pay"): "Take it for ₱budget" (picked at first) or "Offer another price", which opens `OfferFields` (price + note).
  The pinned bottom (`RequestFooter`, `sticky-footer`) holds one action: **Send offer** (full width); while changing a
  sent offer, the price row turns into `OfferFields` and the bottom shows **Cancel** + **Save**; picked: **Open chat**.
  "Take back my offer" is a link under the card. What a tap sends is `Services/OfferDraft` (the budget with no note,
  or the typed price and trimmed note; `IsValid` enables the button). The page reads the request from what
  `JobBoard` has loaded (`FindLoadedRequest`: the feed, else the worker's cached `MyOffersAsync` list) and, for a link
  to one not loaded, reads the feed and then the offers again (`FindRequestAsync`); still missing → "This request is
  no longer open". No server endpoint was added for one post.
- **Offers (inDrive style, `016-schema-job-offers.sql`, table `JobOffers`):** on a request's own page a worker taps
  **"Take it for ₱budget"** or **"Offer another price"** (`OfferFields`: their price, same range as a budget,
  and an optional note up to 300 letters, `JobOfferRules`). Once sent the page shows "Your price ₱…, waiting for the
  customer" with "Change" and a "Take back my offer" link. One offer per worker per post (a new price
  replaces the old one, `UX_JobOffers_PostPro`). The server takes offers only from a published listing of the post's
  trade, on an open post that isn't the worker's own, and never between two people where one blocked the other
  (`JobPostStore.OpenPostFor`). The feed carries the worker's own price (`myOfferPesos`).
- **Picking:** the household's card says **"See N offers"** (`offerCount`), opening `OffersPage`
  (`JobPostRoutes.Offers(id)` = `/posts/{id}/offers`, inside `SeekerLayout`). Each `OfferCard` is the worker's
  `ProCard` as in search (photo, stars, badges; "Takes your budget" when the price is the budget), their price, how far
  they are from the post (whole km) and their note, with "See profile" (Back returns to the offers:
  `SeekerRoutes.Pro(id, back)`) and **"Pick"**, which asks once more. Order: the picked one first, then the lowest
  price, then the earliest. Picking (`POST job-posts/{id}/offers/{offerId}/pick`, one transaction) marks the offer
  `picked` and closes the post, so it leaves every feed; the app then sends the worker a first message ("I picked
  your offer of ₱…") and opens the chat: the Seeker still starts every chat, and a customer's message rings the
  worker. The household's card then says "You picked a worker" with **Open chat** (`pickedProId`).
- **A worker's own offers:** Requests → **My offers** (`JobPostRoutes.MyOffers`, `MyOffersPage`, one `RequestRow`
  each; `GET offers/mine` → `JobPostStore.MyOffersAsync` → `MyOfferDto`, `JobBoard.MyOffersAsync`, read fresh on each
  visit): newest change first, at most 50, each with the service, the budget, the place and the worker's price
  or state on the row (the note and Open chat on the request's page), and its state (`MyOfferStates`: `waiting` while the post is open, `picked` with the `chatId` the
  household started (**Open chat**), `not-picked` once the post closed without them). Offers taken back, hidden posts
  and blocked people are left out. Before, a worker who wasn't picked only saw the post leave the feed.
- **Verified two-way reviews** (brief item 12, `PickedJobStore`, `PickedJobFunctions`, `018-schema-job-done.sql`):
  a picked offer is the job record. Each side marks it done (`POST picked-jobs/{postId}/done`, `JobOffers.HouseholdDoneAt`
  / `WorkerDoneAt`), in any order; both marks make a **completed job** (`PickedJobStore.Completed`). Then the
  household's review of that worker (still `PUT reviews`, one per pair) needs no chat and no 24 h wait and comes back
  with `ReviewDto.VerifiedJob` (computed when read, so an older review becomes verified too); `ListingDto.CompletedJobs`
  counts them; the worker can rate the household (`PUT household-reviews`, table `HouseholdReviews`, `403
  no-completed-job` before), and workers see the household's stars on its posts in the feed (`JobPostDto.HouseholdReviews`).
  Reviews after a chat without a pick still work as before, without the label. Done is each side's own word: no money
  passes through the app. App: `JobBoard.PickedJobsAsync` / `MarkDoneAsync` / `RateHouseholdAsync`, models
  `PickedJob`, `Review.VerifiedJob`, `ProfessionalListing.CompletedJobs`, `JobPost.HouseholdStars`. Screens: both chat
  pages (`ThreadPage`, `ProChatPage`) show the newest picked job as `Components/JobPosts/PickedJobCard` (title, service
  and price, where each side stands, **Mark done** until this person did; then the household's Leave a review link, or
  the worker's stars and note for the household right on the card). Marking done sends no chat message, so while the newest job waits on the other side both pages re-read it every `PickedJobWatch.Interval` (10 s, paused while the app is hidden). A completed job (any of them, an earlier one too) seen on the Seeker's chat page
  tells `SeekerWorkspace.CompletedJobWith`, so `CanRate` opens the review page at once. `ReviewRow` shows a green
  "Verified service" chip (`Review.VerifiedJob`; copy says service, never job), `ListingFacts` a "Done through Tarbaho:
  N" fact, and a worker's `JobPostCard` the household's stars.
- **Blind two-way reviews** (no schema change, computed from the existing times): if one side's review showed first,
  the other could answer it in kind, so people would inflate their stars out of fear. After a completed job, a review
  either side writes (or changes) from then on stays **hidden until the other side has reviewed since that job too, or
  `ReviewRules.BlindFor` (14 days, `SideGigPh.Contracts`) after the job** (`ReviewRules.IsHidden`, the rule in C#;
  the job is completed when its second "done" mark lands). The server applies it as SQL in
  `SideGigPh.AzureSQL/BlindReviewFilter` (`Shown`, one per review table) everywhere a review reaches someone else: the
  worker's reviews (`ReviewStore.ForProfessionalAsync`, the worker too), a Seeker's written reviews read by anyone
  else (`BySeekerAsync`), the stars and count on every listing (`ProfessionalStore.WithReviewsAsync`, so
  `SearchRanker` never sees a hidden review) and a household's stars on its posts (`PickedJobStore.HouseholdStarsAsync`).
  The writer always sees their own, marked `ReviewDto.Hidden` (`ReviewRow` says "Only you see this for now"). A review
  written before the job (a one-way review 24 h after a chat) stays as it was, and reviews with no completed job are
  not blind. Saving a household review clears the search cache, since it can open the household's review.
  `PickedJobDto` carries `CompletedAt`, `TheyReviewed` (the other side reviewed since the job; its stars stay hidden)
  and `TheirRating` (only once it shows). In the app, `Services/BlindReviews.StageOf` (`BlindReviewStage`:
  `WaitingForMe`, `WaitingForThem`, `Open`, `WindowClosed`) words the line under the `PickedJobCard` status: "Your
  review stays hidden until {name} reviews you too, or in N days", "{name} already reviewed you. Send yours to see it",
  "Waiting for {name} to review you…", then "{name} gave you N of 5 stars"; the household's review page opened from the
  card (`SeekerRoutes.RateAfterJob`, `?job=true`: a bool query value must be `true`/`false`) says the worker won't see it until they review too.
  **Locked once both show:** otherwise a side could lower their stars after seeing the other's. A review written since
  the pair's latest completed job locks when the other side's review of it shows too (they reviewed since the job, or
  the 14 days passed): `ReviewRules.IsLocked`, checked by `BlindReviewFilter.IsLockedAsync`. `PUT reviews` and `PUT
  household-reviews` then answer `403 review-locked` (`ReviewOutcome.Locked`, `HouseholdReviewOutcome.Locked`), and
  Start over (`DELETE reviews/mine`, `ReviewStore.DeleteWrittenByAsync`) keeps locked reviews (deleting the account
  still removes everything). A hidden review can still change; a newer completed job opens it again (blind again);
  one-way chat reviews never lock. The writer is told: `ReviewDto.Locked` (own reviews only) and
  `PickedJobDto.MyReviewLocked`. In the app `SeekerWorkspace.ReviewLocked` makes `CanRate` false, so the thread shows
  `Copy.ReviewLockedNote` ("Reviews can't be changed once both are shown") instead of Edit your review, "Your reviews"
  lists it without the edit link (`ReviewRow` adds a lock line), and `PickedJobCard` drops its Change buttons for the note.
- **Phone numbers stay private until a pick** (brief item 11): `ProfessionalStore.ToDto` leaves
  `ListingDto.MobileNumber` empty (the field stays for older apps, whose Call then fails with "couldn't open your phone
  app"), so search, profiles and offers never carry it; `GET professionals/{id}` for the caller's own id and the
  publish answer put it back (`GetAsync(withNumber)`). Before a pick the two talk only in the app's chat, which stays
  as the record. `GET contacts/{otherUid}` (`JobPostStore.ContactNumberAsync`) answers `ContactDto(phoneNumber)` once
  a `picked` offer links the caller and the other person (either side), else null; also null with a block either way
  or no number (a worker's is their listing's, a household's the account's, which a Google sign-in may lack). Both
  chat pages ask for it on open (`JobBoard.ContactNumberAsync`): the Seeker's `ThreadPage` shows **Call** (still
  logged in the chat, `SeekerWorkspace.CallAsync(pro, number)`) and "you can call each other now", or "numbers stay
  private until you pick their offer"; the worker's `ProChatPage` shows **Call** (not logged) and "they picked your
  offer".
- **Notifications** (brief item 10, `SideGigPh.Api/JobAlerts`, called inline by `JobPostFunctions` after the write,
  never failing it): a **new post** (`JobPostOutcome.IsNew`, so a retry answered with the post already there doesn't
  ring again) rings the workers `JobPostStore.WorkersToAlertAsync` finds: the same match as the feed (trade, within
  the worker's own `RadiusKm` of the post or a town match when a point is unknown, never the household or a block
  either way), the best `MaxWorkers` (30), a service they offer first, then nearest. Title "New request near you",
  body "₱budget · first line of the description", tag `post-{id}`, Android channel `requests` (loud). A **new or
  changed offer** rings the household: "New offer: {worker}", "₱price for your post", tag `offers-{postId}` (one
  line per post), channel `offers` (loud: offers are what a household waits for). Both carry `PushData.PostId` and
  `Side`; `ChatAlerts.PathFor` opens `JobPostRoutes.Feed` (worker) or `JobPostRoutes.Offers(id)` (household); older

## Cold starts and double taps

- **Warm-up:** the Function App (Flex Consumption) and the serverless database both go cold when nobody uses them; the first search then waited ~15 s on 4G. `Services/ServerWarmup` (rule, tested) calls the `IServerWarmup` port (`Api/ApiServerWarmup` → `GET warmup`, signed-in, `204`) from `App` when the window opens and on `Resumed`, at most once per `ServerWarmup.IdleAfter` (5 min). The function checks the token (which also loads Google's signing keys) and `WarmupStore.WakeAsync` runs `SELECT 1`, skipped when that instance already did within `WarmupStore.AwakeFor` (1 min). Signed-in only, so nobody outside can keep the database awake and billed. A failed warm-up is only a trail line. The first wake on each instance also compares `dbo.SchemaChanges` with `SchemaScripts.Required` (every `NNN-schema-*.sql` after 001, checked against the folder by `SchemaCheckTests`) and, if a script was never run, logs an error and saves an `ErrorReports` row naming it (on 15 Nov a missing `011-schema-safety` made every search and Inbox answer 500 for a morning).
- **One tap, one call:** every tap handler that calls the API, the sign-in provider (SMS costs money) or the camera returns early while `_busy`; `Disabled="_busy"` alone is not enough, since a second tap can arrive before the re-render. Handlers catch failures into a message (`MePage` Start over shows `CommonCopy.StartOverFailed`).
- **A screen that throws:** `MainLayout` wraps the page in `AppErrorBoundary` (skeleton), which logs the exception through `ILogger` (so `ErrorLogLoggerProvider` makes it an error report) and shows `CommonCopy.ScreenBroke` with a button back to `/`; any navigation clears it. When the exception is a lost connection (`NetworkErrors.IsNetwork`: an `HttpRequestException` with no status code (the `ApiClient` wraps Android's socket errors in one), a `WebException`/`SocketException`, a request timeout; a server's error answer, a plain cancel and file errors such as "No space left on device" are not), it shows `CommonCopy.NoConnection` with **Try again** instead, which rebuilds the same page so it loads again. While the phone is offline (`INetworkStatus`, `DeviceNetworkStatus`), `ConnectionBanner` shows a gray `CommonCopy.Offline` strip above the page once the phone has been offline for `ConnectionBanner.ShowAfter` (3 s, so a one-second 4G drop doesn't move the page under the person's finger) and hides it when the connection is back; the strip is sticky (`--app-offline-banner-height`, the top bar sits under it through `body:has(.app-offline-banner)`), so it shows on a chat that opened scrolled to its end. `BusyOverlay` swaps its rotating lines for `CommonCopy.BusySlow` (offline: `BusyOffline`) once a wait passes `SlowAfter` (12 s). A chat's send error is `ChatComposer.Error`, inside the pinned box (an alert above it was covered by it). Search hides its "0 for you" line while offline. **Empty or offline:** reads log and come back empty, so an empty list can mean "no internet". A list read from the server passes `OnRetry` to `EmptyState` (search results, both Inboxes, my posts, the Requests feed, a post's offers, My offers); while offline it shows `CommonCopy.NoConnection` with a WifiOff icon and **Try again** instead of its "nothing here" line, and calls `OnRetry` by itself when `INetworkStatus` says the connection is back. An `EmptyState` without `OnRetry` (photos not yet picked) never changes. **Slow 4G:** `ApiClient` cancels a GET after `ReadTryLimit` (30 s, so two tries match the old 60 s timeout a cold server and paused database may need) and tries once more (`ReadTries` 2), then fails as a lost connection (`HttpRequestException` without a status); writes (POST/PUT/DELETE) are sent once, since a retry could repeat them. When a next page never arrives, `LoadMoreOnScroll` stops loading on its own and shows `CommonCopy.LoadMoreFailed` with **Try again**. **Pushes while open:** `ProLayout` / `SeekerLayout` refresh the Requests feed / my posts (with the Inbox) when a notification arrives in the foreground. On Android, a lost connection that escapes every catch reaches `AndroidEnvironment.UnhandledExceptionRaiser`, which marks it handled (reported as `Crash.Network`, the app keeps running); anything else still crashes.

The rules live in **`Services/OnboardingSteps`** (`ProStep` / `SeekerStep`, `FirstUnanswered`, `StepToShow`, `PickTrade` / `ToggleTown` / `ToggleAllTowns`, `PickCategory` / `PickTown`, `NextPath`, `BackPath`, and `LaunchPath` for `LaunchRouter`), so they are tested; the interview pages only call them, save and navigate.
- **Money is the hook on both sides. Prices are per job** (`Services/Pricing`): every job has a price guide in Azure SQL (`Services.PriceMin` / `PriceAverage` / `PriceHigh`, pesos, labor only, `008-schema-service-prices.sql`, filled by `004-config.sql`; in the app `ReferenceData.Prices` / `AppConfig.Prices`, in `GET config` `ServiceDto.Price`), and no job's lowest price is under the **NCR daily minimum wage** (`ConfigOptions` `minimum-wage`, ₱755, Wage Order NCR-28; `ReferenceData.MinimumWage`, `ConfigDto.MinimumWage`; `CanUse` refuses a config that breaks it). A **Skilled Worker's rate** (`RateTierId`) is a point of each job's guide, `ReferenceData.RateLevels` = `PriceLevels` (Contracts) `minimum` / `average` / `above-average`, or `quote`; the rate tiles show each level's prices for their jobs (`Pricing.RateChoices`), cards show the price for the searched job (`ListingText.Rate(listing, serviceId)`), and an old one-scale tier in a saved draft is dropped on load (`OnboardingCleanup.DropOldRate`) so the rate is asked again. A **Seeker's budget** (`BudgetId`) is a peso range string (`BudgetRange` in Contracts: `"800-1500"`, `"1500-up"`; old tiers `500-1000`/`under-500`/`5000-up` read the same way): the budget step anchors on the job's average ("Karaniwang bayad…"), offers lowest–average, average–above, above-and-up (`Pricing.BudgetChoices`), **"Other amount"** (two peso boxes, `Onboarding/BudgetRangeFields`, from ≥ the minimum wage, to ≥ from: `Pricing.IsValidBudget`) and "Not sure yet". The server ranks budget fit by price vs the range's top (`RankScales.PriceOf`), which also drives the "Pasok sa budget mo" badge. `ReferenceData.PriceTiers` stay in the config only for app versions before price guides. Income goals stay in the config only for app versions that still ask the earnings goal.
- **Everyone signs in first** (owner decision), right after the language question: **phone number + SMS code** as the main option (it verifies the number), **Continue with Google** below it. A phone sign-in is asked its name once (`/verify/name`). A Google account brings its name; only a Skilled Worker must **add a verified number** (`/verify/phone`, linked to the same account) before **Publish** (`/professional/publish`), which asks `SignInGate.RedirectAsync(..., requirePhone: true)`. **Seekers are never made to add a number**: they search and chat with a Google sign-in as it is, and use the phone sign-in only if they choose it. The interview answers stay on the phone (`IOnboardingStore`).

## Auth

Auth is provider-neutral. The contract and screens live in the skeleton; the vendor is an adapter in its own project.

- **Contract (skeleton, `MobileAppTheme/Auth/`):** `IIdentityProvider` (phone code, Google, current user, sign-out, and `Methods`, the `AuthMethods` it supports) with `AuthUser`, `AuthResult` and `PhoneVerification`. A failure is an **`AuthError`** (`Cancelled`, `Network`, `InvalidCode`, `InvalidPhoneNumber`, `PhoneInUse`, `TooManyAttempts`, `Misconfigured`, `NotAvailable`, `Unknown`) plus the provider's raw `Detail` for logs. The UI shows `AppText.Describe(error)` (`CommonCopy`, English/Taglish), never provider text.
- **Screens (skeleton, `MobileAppTheme/Components/Auth/`):** `AuthPage` (route **`/verify`**: brand + tagline, then only the methods the provider offers: the phone code first for everyone, then "or" Apple/Google), `NamePage` (**`/verify/name`**, once when the account has no name), `AddPhonePage` (**`/verify/phone?then=…&back=…&skip=true&later=…`**, links a verified number to the signed-in account; Back goes to `back`, else home; `skip` adds "Do this later" → `then`, for an early ask a later page repeats; `later` adds it → that path, for a page that needs the number: Publish sends it to Pro home, whose purple not-live banner then says "Confirm your number to publish", so a worker out of SMS codes for today is never stuck), `PhoneSignIn` (`LinkToCurrentUser` for linking; rationed by **`SmsSendLimit`**: a new code only 360 s after the last, at most 3 in 24 h per phone, kept in Preferences by `PreferencesSmsSendHistory`, with a countdown on "Send a new code"; the sixth digit sends the code without a tap; signing in, it also goes on by itself once the provider has someone signed in with the number the code went to, since Android may read the SMS and confirm the number while the code step is open, and the Firebase adapter then answers a typed code refused as used with that sign-in) and `GoogleSignInButton`. **`SignInGate`** (`MobileAppTheme/Auth/`) is what pages ask: it returns the missing step (sign in, name, phone) or null, and lets everyone through when no provider is registered. Routes are in `AuthRoutes`.
- **App hooks:** `IAuthLanding` says where to go after sign-in. SideGigPh keeps the skeleton's `HomeAuthLanding` (`/`): the launch router restores a worker's live listing on a phone with no answers (`ListingRestore`) and resumes onboarding or opens their home. `IPhoneNumberFormat` reads typed numbers into E.164; SideGigPh's `PhilippinePhoneNumberFormat` accepts 0917… / 917… / +63 917… and sets the optional `Region` ("Philippines (+63)"), shown read-only above the number like Airbnb's Country/Region box. Skeleton defaults (`TryAdd`): `NoIdentityProvider` (no sign-in, `Methods = None`), `HomeAuthLanding` (`/`) and `E164PhoneNumberFormat`.
- **Adapter: `MobileAppTheme.Firebase/`** (Android/iOS MAUI library, `Microsoft.NET.Sdk`, not Razor, so no WebView asset clash). `FirebaseIdentityProvider`, `FirebaseAuthErrors` (status-code decoding) and `FirebaseAuthSetup`: `builder.AddFirebaseAuth(GoogleWebClientId)` in `MauiProgram` initializes the SDK in the platform lifecycle (wrapped, so a missing config doesn't crash launch) and **replaces** the skeleton's `IIdentityProvider`. `GoogleWebClientId` (the web OAuth client, client_type 3, from `google-services.json`) is a constant in `MauiProgram`.
- **Auth error policy:** an adapter never reduces an auth-infra exception to a bare message. It logs the full exception (type + stack) to Logcat/Output and returns an `AuthResult` with a mapped `AuthError`. For Google sign-in, `FirebaseAuthErrors.FromGoogle` parses the Google Play status code out of the exception message (which is just `"7:"`, `"10: …"`), with no dependency on the Play-services binding: `7` → `Network`, `10` DEVELOPER_ERROR / `12500` → `Misconfigured`, `12501` → `Cancelled`. A wrong SMS code (`FirebaseAuthException` `InvalidCredential`) → `InvalidCode`. `SignUpWithPhoneAsync` logs then rethrows (fail fast). Phone sign-in checks the app with Play Integrity (the Play Integrity API must be on, `firebase/cloudshell-auth.sh`); on an emulator that always fails with 17028 "Invalid app info in play_integrity_token", so `AddFirebaseAuth` forces the reCAPTCHA check there (`DeviceType.Virtual`), never on a real phone.
- **Packages (in `MobileAppTheme.Firebase`, `PrivateAssets="none"` so their build targets reach the app and process `google-services.json`):** `Plugin.Firebase.Auth` 3.1.1 + `Plugin.Firebase.Auth.Google` 3.1.2 + `Plugin.Firebase.CloudMessaging` 3.1.2 (the **modular** packages — NOT the bundled `Plugin.Firebase`, which drags in Crashlytics and crashes at launch in MAUI). Android **requires** `MainActivity.OnActivityResult` to call `FirebaseAuthSetup.HandleActivityResult(...)`; without it `SignInWithGoogleAsync()` hangs forever (no exception, stuck on "connecting"). `HandleActivityResult` forwards only while a Google sign-in is pending (`GoogleSignInPending`): the photo picker's and dialer's results reach `OnActivityResult` too, and the plugin's handler throws a `NullReferenceException` (shown as `Android.Runtime.JavaProxyThrowable`) that kills the app when nothing is waiting. The app's debug/release **SHA-1 (and SHA-256 for phone auth) must be registered in the Firebase console** and `google-services.json` re-downloaded — otherwise Google sign-in returns `DEVELOPER_ERROR` (status 10) and phone verification fails app-attestation.
- **Android signing ([`docs/android-signing.md`](android-signing.md)):** every build on every PC and in CI is signed with the committed shared dev key `Platforms/Android/Signing/dev.keystore` (alias `androiddebugkey`, password `android`; SHA-1 `A5:F0:C9:…:31:B6` registered in Firebase), so sign-in works everywhere without registering per-machine keys. A Release build switches to the store key only when `ReleaseKeystore` (or env `SIDEGIGPH_KEYSTORE`) points at an existing file. The passwords come from env `SIDEGIGPH_KEYSTORE_PASS` / `SIDEGIGPH_KEY_PASS` and are never in the csproj. Other keystores are git-ignored. CI writes `google-services.json` and the optional store key from secrets (`GOOGLE_SERVICES_JSON_BASE64`, `ANDROID_KEYSTORE_BASE64`, …). Google Play's App signing key needs its own fingerprints in Firebase.
- **Firebase config (not committed; required before an Android/iOS run):** `Platforms/Android/google-services.json`, `Platforms/iOS/GoogleService-Info.plist`, plus a Google OAuth client (Android SHA-1; iOS reversed-client-id URL scheme). The app's csproj references the config files with `Condition="Exists(...)"` so the build works without them.

### Switching the auth provider

Nothing outside the adapter project and `MauiProgram` knows the provider is Firebase. To move to another one (Supabase, Azure AD B2C, Auth0, a custom backend…):

1. Create `MobileAppTheme.<Provider>/` next to `MobileAppTheme.Firebase/`: a class implementing `IIdentityProvider` with its `Methods`, mapping every failure to an `AuthError` (log the full exception first), and a `builder.Add<Provider>Auth(...)` extension that does its setup and `Replace`s `IIdentityProvider`. Load the `maui-firebase-auth` skill for the error policy and the `mobile-app-theme` skill for the boundary rules.
2. In `SideGigPh.Maui.csproj`, swap the `MobileAppTheme.Firebase` project reference for the new one; in `MauiProgram`, swap `AddFirebaseAuth(...)` for the new call; in `MainActivity`, remove the `FirebaseAuthSetup.HandleActivityResult` line (or replace it with what the new SDK needs).
3. Remove the Firebase config files and `GoogleWebClientId` if nothing else uses Firebase.
4. Users are keyed by `AuthUser.Uid`; the new provider's ids differ, so existing accounts need a migration (once there are real accounts).

Never call a provider SDK from a page, workspace or service. If the UI needs something the contract lacks (e.g. email sign-in), add it to `IIdentityProvider` / `AuthMethods` / `AuthError` in the skeleton first, then implement it in every adapter.

## Pictures

**Pictures are the app's own images, never emoji**: one small SVG per trade, job, answer and interview question in `SideGigPh.Maui/wwwroot/images/icons/` (shipped in the app, so they show offline and look the same on every phone), all in one look: a 48-unit box, 2.5 ink outlines with round ends, the light brand tint `#E9DFF3` and one brand-purple detail (the colors are written in the files and must match `AppTheme`). `Services/AppImages` names them: `AppImages.For(id)` picks a trade's, job's or answer's picture by its stable id ("Others" and an id without a picture get the plus, `AppImages.More`), and the question pictures are its fields (`AppImages.Trade`, `Town`, `Price`…). `CatalogOption.Icon` / `ChoiceItem.Icon` / `InterviewStep.Illustration` hold the image path; the skeleton's `ChoiceTile` and `InterviewStep` and the app's `CategoryRail` draw it with `MudImage`. The `Icon` emoji in `004-config.sql` stays for app versions before the pictures and is not shown (`ApiMapping.ToModel`); a saved config that still has emoji is refused by `ReferenceData.CanUse`. A new trade or job needs a new SVG in the same look plus a line in `AppImages` (`AppImagesTests` checks every id has a picture and every picture is a file).
