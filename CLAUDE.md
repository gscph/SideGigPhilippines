# SideGigPh — Tradesmen Open Directory (Philippines)

## What This Is

A high-density open local service directory (Carousell/Craigslist style) connecting urban households with skilled tradesmen and home-service pros. The categories (trades) are Aircon Technician, Plumber (Tubero), Electrician, Roofing & Gutter, Carpentry (Karpintero), Welder, Masonry (Mason), Car Mechanic (Mekaniko), Errands/PasaBuy and Solar Panel Technician. **They live in Azure SQL** (`Categories` / `Services`, filled by `SideGigPh.AzureSQL/Sql/004-config.sql` with the other answer lists in `ConfigOptions`: towns, price tiers, experience, urgency, income goals) and reach the app in one **config** document, the public `GET config` (see App config below): `ReferenceData.Categories` / `ServicesByCategory` / `Cities` / `PriceTiers`… read it; `ReferenceData.BuiltInConfig` is the copy shipped for the first launch offline and must match `004-config.sql` (an integration test checks). Use `ReferenceData.ServicesOf(categoryId)`, never `ServicesByCategory[...]`, since a trade can disappear. **Category and service IDs are stable; only labels change.** A trade we stop offering is retired (`IsActive = 0`, kept in `004-config.sql`, e.g. `home_massage`), never deleted or reused; saved answers naming it are dropped on load (`OnboardingCleanup.DropRetiredJobs`). Each category's services are ordered most-requested first and end with **"Others / Wala sa nabanggit"** (`…-other`, `ReferenceData.IsOtherJob`). Picking it shows `Onboarding/OtherJobField` so the person can type the job (`SeekerAnswers` / `ProfessionalDraft.OtherJobText`); the job stays "Others", and the text is sent once for analytics (`OtherJobNotes.NoteAsync` → `POST other-jobs` → table `OtherJobNotes`, never shown; it also words the Seeker's first message). Neutral "Yellow Pages" model — direct consumer-to-tradesman contact, zero transaction commissions.

**Target region (MVP):** three Rizal towns, **Angono, Antipolo and Taytay** (`ReferenceData.Cities`). Coverage was briefly four areas (Metro Manila, Rizal, Laguna, Cavite) and was cut back on purpose.

**Town IDs are stable** (no accents: `taytay`, `angono`, `antipolo`); only labels change. All towns sit in one area, `ReferenceData.ServiceAreaId` (`rizal`), which is **never asked**: `ReferenceData.AreaOf(cityId)` gives it (null for a town we don't serve), the interviews set `AreaId` from the town(s), and listings and search still carry it, so more areas can return without a schema change. A Skilled Worker ticks **any number of the towns** they go to; a Seeker picks **one home town**. Saved answers naming a town we no longer serve are cleaned on load (`Services/OnboardingCleanup`, called by `FileOnboardingStore`), and `LaunchRouter` reopens the town question for a finished interview that lost its town.

**Audience:** many Professionals (tradesmen) are not confident English readers. The app is **English / Taglish**, and the user picks one on the very first screen.

## Tech Stack

- **Frontend:** .NET MAUI Blazor Hybrid — shared Razor Class Library for Android and iOS
- **Target platforms:** Android + iOS only (Windows and Mac Catalyst are not supported)
- **UI:** Mobile-first. Component library: **MudBlazor** (9.x, version set once in `MobileAppTheme.csproj`). Providers (`MudThemeProvider`, `MudPopoverProvider`) sit in the skeleton's `MainLayout`; MudBlazor's and the skeleton's CSS/JS load from the app's `wwwroot/index.html`
- **App skeleton:** **`MobileAppTheme/`** is a reusable Razor class library (plain `net10.0` + `Microsoft.Maui.Essentials`) holding the shell, theme builder, generic components, localization and on-device adapters. `SideGigPh.Maui` references it; the skeleton never references the app, so the next MVP can start from it. See [`MobileAppTheme/README.md`](MobileAppTheme/README.md) and the `mobile-app-theme` skill.
- **Auth (MVP):** Firebase Authentication — Phone/SMS OTP + Google login. Firebase is the sign-in provider and sends the new-message notifications (Cloud Messaging, below); its console setup and the SMS-region script are in [`firebase/`](firebase/README.md)
- **Database:** **Azure SQL** — users, listings, reviews, chats, the app config (trades and jobs, towns, price tiers…). The phone never connects to it: the app calls **`SideGigPh.Api`**, which checks the Firebase ID token and uses **`SideGigPh.AzureSQL`** (EF Core 10, `Microsoft.EntityFrameworkCore.SqlServer`). **The schema is the T-SQL in `SideGigPh.AzureSQL/Sql/`** (`001-schema.sql` the first release's tables/keys/indexes, **frozen: the database is live**, so every later change is a new guarded, numbered script `NNN-schema-<what>.sql` (first: `005-schema-ranking-signals.sql`), run by hand before the API that needs it, recorded in `dbo.SchemaChanges`; load the `db-migration` skill; `004-config.sql` the trades, jobs and other answer lists (required data, an idempotent upsert that retires what it no longer lists), `002-seed.sql` sample workers and reviews with ids `seed-…`, no chats or photos); there are no EF migrations, so `SideGigPhDb.cs` must match 001 plus every later schema script. The connection string is the Function App setting **`SqlDatabase`** (or the git-ignored `local.settings.json`), never in the phone app. Plan, tables and routes: [`docs/data-model.md`](docs/data-model.md); setup: [`azure/`](azure/README.md)
- **Photos (MVP):** Azure Blob Storage (storage account `sidegigphbfb9`, also the Function App's own storage; container `photos`, blob `{sha256}.jpg`, readable by URL), written only through **`SideGigPh.Api`** (Azure Functions, isolated worker, .NET 10, published to the Function App `SideGigPhApi`, https://sidegigphapi-hrb9bgerbgcgawbm.southeastasia-01.azurewebsites.net/api/). The API checks the user's Firebase ID token, re-encodes every upload the same way (`PhotoImage`: upright, sRGB, at most 1280px on the long side and never enlarged, progressive JPEG quality 82, EXIF/GPS stripped; screens crop with object-fit cover), hashes the result and refuses a photo another account already stored (anti-fraud rule 2). Photos show straight from their public blob URL, so the container must allow blob-level anonymous read: the API switches a private `photos` container to it on first upload, and fails with a clear message when the account blocks anonymous access (`azure/cloudshell-setup.sh` turns it on; `cloudshell-verify.sh` checks it). **The storage connection string lives only in the Function App's settings (`PhotoStorage`)** or, on a PC, the git-ignored `SideGigPh.Api/local.settings.json`; never in the phone app. Setup and checks: [`azure/`](azure/README.md). The app reaches it through **`ApiPhotoStore`** (`SideGigPh.Maui/Services/Api/`, registered in `MauiProgram` after `AddMobileAppTheme`, so it replaces the skeleton's `FilePhotoStore`): `POST photos` uploads, `DELETE photos/{id}` removes, each with the user's ID token (`IIdentityProvider.GetIdTokenAsync`). The server's returned id is the photo id; photos show from their public blob URL. The API URL and blob base URL are constants in `MauiProgram` (not secrets).
- **Shared contracts:** **`SideGigPh.Contracts`** (plain `net10.0`, no dependencies): the JSON records the app and the API send each other (`ListingDto`, `ChatDto`, `PublishListingRequest`, `SearchPageDto`…, `Wire` strings, `ApiErrors` codes, `Paging` page sizes) and the source-generated `ApiJson` context. Every new contract type and its `List<T>` needs a `[JsonSerializable]` line there (trim-safe on the phone)
- **Future migration:** PostgreSQL/PostGIS for spatial queries (`ST_DWithin`): only `SideGigPh.AzureSQL` changes
- **Tests:** **`SideGigPh.Tests`** (plain `net10.0`; xUnit 2, FluentAssertions **7.x** (8+ needs a paid licence for commercial use), `Microsoft.AspNetCore.TestHost`, coverlet). `Unit/` (by feature, fakes in `TestSupport/`, no network or database) and `Integration/` (the real `SideGigPh.Api` functions served in memory at the routes in their `[HttpTrigger]`s, the real stores on a fresh SQL Server database built like live is upgraded (`Sql/001-schema.sql`, then every `NNN-schema-*.sql` in order, then `004-config.sql`; `SchemaScriptTests` re-runs them to prove the guards), the real `FirebaseTokenValidator` with a test signing key, photos in an in-memory blob container, and per test person the app's real services and `AddSideGigPhApi` adapters; trait `Category=Integration`, skipped with a reason when no SQL Server: LocalDB on Windows or `SIDEGIGPH_TEST_SQL`). The app targets only Android/iOS, so the csproj **compiles `SideGigPh.Maui/Models/**` and `Services/**` (plus the `*Routes.cs`) into the tests by link**: keep pages' rules in `Services/` (pages aren't compiled there). Two test seams, unused by the app: `ApiOptions.Handler` (an `HttpMessageHandler` for `ApiClient`) and `FirebaseTokenValidator`'s optional `signingKeys`. Snapshot tests in `Unit/UpdateSafety/` fail on purpose when an id, JSON field name or error code changes. Coverage of the core code is ~100% (`coverage.runsettings`). How to run and what each folder protects: [`SideGigPh.Tests/README.md`](SideGigPh.Tests/README.md); after a relevant change load the `run-tests` skill

## Architecture — Ports & Adapters

All external infrastructure is decoupled behind C# interfaces (Dependency Inversion). On the phone: page → workspace → port → `Services/Api/` adapter → HTTPS → `SideGigPh.Api` function → store in `SideGigPh.AzureSQL` → Azure SQL. Swapping the database touches only `SideGigPh.AzureSQL`; swapping the sign-in provider touches only its adapter project (Auth below).

### Key Ports (Interfaces)

**`IIdentityProvider`** (skeleton, `MobileAppTheme/Auth/`) — Auth abstraction; Firebase is one swappable adapter (see Auth → Switching the auth provider)
- `Methods` (which `AuthMethods` the provider supports)
- `SignUpWithPhoneAsync(string phoneNumber)` (sends the SMS code, for sign-in or linking)
- `VerifyPhoneOtpAsync(string verificationId, string userEnteredCode)`
- `LinkPhoneAsync(string verificationId, string userEnteredCode)` (adds a verified number to the signed-in account, same uid; `AuthError.PhoneInUse` if another account has it)
- `SignInWithGoogleAsync()`, `SetDisplayNameAsync(string)`
- `GetCurrentUserAsync()`, `GetIdTokenAsync()` (the ID token for our own API as a Bearer header), `SignOutAsync()`

> **Naming:** user-facing text (`Copy`, `ReferenceData`, brand tagline) always says **"Skilled Worker"** / "skilled worker" (Taglish too), never "pro", "Professional" or "tradesman". Code keeps **"Professional"** (`ProWorkspace`, `ProfessionalListing`, `/professional` routes, `Professionals` table) for the side-gig service provider (aircon tech, plumber — and also non-trade pros like web developers or video editors), never "tradesman".

**`IOnboardingStore`**: the onboarding answers, saved on the device with no account (`Local/FileOnboardingStore`). It writes one JSON file in `FileSystem.AppDataDirectory`, using a source-generated serializer and an atomic write. There is no SQLite yet; add it when local data needs querying. Don't use the WebView's `localStorage`.

**`IContactLauncher`** (skeleton): Call / Text a pro through the phone's apps (`MobileAppTheme/Services/Local/DeviceContactLauncher`, MAUI `PhoneDialer` / `Sms`). Android needs the `tel` / `smsto` `<queries>` in `AndroidManifest.xml`.

**`IChatRepository`** (`Api/ApiChatRepository`): **in-app chat**, one `Chat` per Seeker and pro (id `{proId}_{seekerId}`, carrying both names, the job from the Seeker's answers and the `LastMessage`) with its `ChatMessage`s (`Text`, or `Call` when the Seeker's Call button opened the dialer). `GetInboxAsync(personId, ChatSide)` is each side's Inbox; unread = the other person wrote last after this side's read time (`MarkReadAsync`); `GetMessagesAsync(chatId, beforeMessageId)` reads one page, `Paging.Messages` (20) per page (`GET chats/{id}/messages?take=20&before={messageId}`; without `take` the server sends every message, for app versions before paging): a chat page opens on the newest page, scrolled to the bottom, and loads the page before its oldest message when the person scrolls to the top (swipes down) (skeleton `LoadMoreOnScroll` `Edge="LoadMoreEdge.Top"`, which keeps the reader's place); the loaded messages live in **`ChatHistory`** (`Services/`: `FromLatest`, `WithOlder`, `WithLatest`, `With`; each workspace's `GetMessagesAsync` / `OlderMessagesAsync` / `NewMessagesAsync`). `Watch(chatId, lastMessageId, …)` gives live updates while a chat is open: it polls `GET chats/{id}` every `ApiChatRepository.WatchInterval` (5 s) and hands back the chat when its last message differs from the one the page shows; the page passes it to the workspace's `ChatChanged` and adds the newest page under what it shows (`NewMessagesAsync`). Only the Seeker can start a chat; the server stamps message times. **`IUserRepository`** (`Api/ApiUserRepository`, `users/me`): the signed-in person's `UserProfile` (account name/number, language, side, private earnings goal, and `ProfilePhotoId`: the account's one profile photo, the Seeker's own or the worker's listing photo, unique across accounts by `UX_Users_ProfilePhoto`), saved by `LocalAccount.SaveProfileAsync` at the role pick, the end of either interview, a language change and a profile-photo change; `SaveDeviceAsync(token, platform)` (`PUT users/me/devices`) registers this phone for notifications. **`IReviewRepository`** (`Api/ApiReviewRepository`): Seekers write one review per pro they chatted with, **only 24 hours after the chat started** (`ReviewRules.WaitAfterChatStarts` in `SideGigPh.Contracts`, shared by both sides; `SeekerWorkspace.CanRate` hides the Rate buttons and `ToRate` until then, and the thread shows `Copy.RateLater`; an earlier review can always be changed) (`SaveAsync` replaces; the server answers `403 no-chat` without a chat and `403 review-too-soon` before then); stars for ranking travel on each listing (`ProfessionalListing.Reviews`, averaged by SQL in the search query). Reviews about a pro survive their Start over.

**New-message notifications** (not SignalR: it only reaches an open app, which already polls): **`IPushNotifications`** (skeleton port, default `NoPushNotifications`; adapter `FirebasePushNotifications` in `MobileAppTheme.Firebase`, added by `builder.AddFirebasePush(channels)` in `MauiProgram` with the two Android channels `PushData.CustomersChannel` (loud) and `RepliesChannel` (quiet)). The server decides how loud: **a customer writing to a Skilled Worker rings** (title "New customer: …" on the first message); **a worker answering a Seeker only puts a red dot on the app icon** (Android: a silent tray line on the low-importance channel; iOS: badge only). One notification per chat (tag / `apns-collapse-id` = chat id), badge = the receiver's unread chats, data `PushData.ChatId` / `ProfessionalId` / `Side`, nothing shown while the app is open (it refreshes the Inbox instead). **`ChatAlerts`** (`Services/`, singleton) is the app side: `ProLayout` / `SeekerLayout` `Attach` it (Inbox refresh on arrival, open the chat on a tap, `ChatAlerts.PathFor`), call `ShowUnread(Workspace.UnreadChatIds)` on every change (read chats leave the tray, the badge follows), and register the phone; the permission is asked only with a reason (`AskAsync`: Pro home opening with a live listing, the Seeker's `ThreadPage` after a send), never at first launch. Android needs `POST_NOTIFICATIONS`, `MainActivity` `LaunchMode.SingleTop`, and the `ic_notification` drawable (the logo path, white) named in the manifest. Server: `ChatFunctions.Send` → `ChatNotifier` (wording, English/Taglish from `Users.Language`) → `IPushSender` (`FcmPushSender`, Firebase Admin SDK, setting `FirebaseServiceAccount`; `NoPushSender` without it); a retried message id or a failed send never notifies twice or fails the message; dead tokens are deleted. Setup: [`firebase/README.md`](firebase/README.md) → Notifications.

**`JsonFile<T>`** (skeleton, `MobileAppTheme/Services/Local/`): the one place that reads/writes an app-private JSON file (atomic temp-file write, corrupt file reads as missing, source-generated `JsonTypeInfo`). `FileOnboardingStore` and `FileConfigCache<T>` (the app config) use it.

**`LocalAccount`** (`Services/`, singleton, also registered as the skeleton's **`IAppAccount`** that `MePage` uses): the person on this phone, whichever side: app language (`SetLanguageAsync`, raises `Changed` for the layouts) and **Start over** (`StartOverAsync`): deletes their photos, published listing, chats, reviews and profile (`DeleteForPersonAsync` on the chat and review repositories, `IUserRepository.DeleteAsync`), clears `IOnboardingStore` (`ClearAsync`) and makes both workspaces `Forget()`, so `/` restarts onboarding at the language screen. With auth it becomes sign-out / delete account.

**Ids:** the signed-in person's uid is their id on both sides (the server always takes it from the token, never the body): `ProWorkspace.MyId` (also the listing id, `Professionals.Id`) and `SeekerWorkspace.MyId`, both set when the workspace loads. Pages compare against those, never a literal. Only when no sign-in provider is registered do they fall back to the old fixed ids `ListingMapper.OwnListingId` (`"own"`) and `SeekerWorkspace.LocalSeekerId` (`"me"`).

**API adapters** (`SideGigPh.Maui/Services/Api/`, the only app code that talks HTTP): `ApiClient` (one `HttpClient`, the Firebase ID token on every request, `ApiOptions(ApiUrl, PhotoBaseUrl)`; its optional `Handler` is for tests only), `ApiProfessionalProfileRepository`, `ApiUserRepository`, `ApiReviewRepository`, `ApiChatRepository`, `ApiConfigRepository`, `ApiPhotoStore`, and `ApiMapping` (contracts ↔ `Models/`; models never get contract types). `AddSideGigPhApi(options)` registers them all in `MauiProgram`, after `AddMobileAppTheme`. Reads that fail (offline, server error) are logged and come back empty (`ApiClient.ReadAsync`); writes log and throw (`EnsureWritten`), and the pages already show a "didn't send / didn't publish" message. A listing sends photos by id (read from their blob URLs); the server stores ids and builds URLs.

**Round trips and caching** (each window is a named constant): `ApiProfessionalProfileRepository` keeps each page of search results for `SearchFreshFor` (60 s, per query and page: the server ranks, so a changed town, budget or job is a new request) and a listing for `ListingFreshFor` (5 min, filled by searches too; the Inbox and profile reuse it), both in `TimedCache<T>` (successful reads only); its publish/remove drops them. Each workspace's `RefreshActivityAsync` reads its lists side by side; tab pages call `RefreshIfStaleAsync` (skips within `ActivityFreshFor`, 15 s). Writes never re-read everything: a send, reply or mark-read updates the list from the server's answer (`Put`), and the chat page appends the saved message. Server side, `ListingCache` (`SideGigPh.AzureSQL`, `IMemoryCache`) keeps a trade's listings 30 s per instance (the next pages of a search rank that same list again) and is cleared by a publish, removal or review on that instance.

**Server** (`SideGigPh.Api` + `SideGigPh.AzureSQL`): one function class per area (`UserFunctions`, `ProfessionalFunctions`, `ReviewFunctions`, `ChatFunctions`, `PhotoFunctions`, `ConfigFunctions`), each checking the token first (`FirebaseTokenValidator.GetUidAsync` / `GetCallerAsync`, which also gives the verified `phone_number`) (the one public route is `GET config`, reference data read before the account is ready; `ApiWiringTests.PublicRoutes`), then calling a store (`UserStore`, `ProfessionalStore`, `ReviewStore`, `ChatStore`, `PushDeviceStore`, `ConfigStore`, `OtherJobNoteStore`) that holds the data rules and answers with contracts or an outcome enum. Errors answer `{ "error", "detail" }`: `ErrorDetailsMiddleware` turns any exception into `500 exception` (or `400 bad-body`) with the stack trace in `detail` while `ApiResults.ShowDetails` is on (MVP debugging; turn it off before launch), and the app logs the whole answer (`ApiClient.EnsureWrittenAsync`). Multi-row writes use `db.InTransactionAsync` (retry-safe on Azure SQL); a caller's own data sits under `…/me` / `…/mine` routes. Settings: `PhotoStorage`, `SqlDatabase`, `FirebaseProjectId`, `FirebaseServiceAccount` (notifications; optional).

**`IPhotoPicker`** (skeleton `Local/DevicePhotoPicker`, MAUI `MediaPicker.PickPhotosAsync`, resized to 1280px; `PickAsync` returns a `PhotoPick` whose `PhotoPickStatus` is `Picked`, `Cancelled`, `PermissionDenied` or `Failed`, and `OpenAppSettings()` opens the app in Settings) and **`IPhotoStore`** (skeleton default `Local/FilePhotoStore`; SideGigPh uses `Services/Api/ApiPhotoStore`, see Photos above): photo id = SHA-256 of the bytes (anti-fraud rule 2). `FilePhotoStore` keeps files in `AppDataDirectory/photos` shown as data URLs; `ApiPhotoStore` shows https blob URLs. `SaveAsync` throws `PhotoStoreException` when the upload fails (`Taken` = another account has this photo, the API's `409`). `ProWorkspace` turns pick and upload outcomes into a `PhotoAddResult.Problem` (`CouldNotOpen`, `NoPermission`, `UploadFailed`, `Taken`) and `PhotoAddNotice` shows a different message for each (no permission adds an Open Settings link); `DeleteAsync` logs a failure and carries on. Gallery-only, no camera, so Android 13+ and iOS (system photo picker) need no permission; on Android 12 and older `DevicePhotoPicker` checks and asks for `Permissions.StorageRead` first (the manifest has `READ_EXTERNAL_STORAGE` `maxSdkVersion=32`; iOS has `NSPhotoLibraryUsageDescription`). On Android the app's `ILogger` output also goes to logcat (`Platforms/Android/LogcatLoggerProvider`, Information and up, with full exceptions): `adb logcat -s SideGigPh`.

**`IProfessionalProfileRepository`** (`Api/ApiProfessionalProfileRepository`): `SearchAsync(query, skip)` (`GET search/professionals?categoryId=…&areaId=…&serviceId=…&cityId=…&budgetId=…&skip=…&take=4`: one page of results **ranked on the server**, a `SearchPageDto` with both groups' totals; the old unranked `GET professionals?categoryId=…&areaId=…` stays for app versions before paging), `GetByIdAsync` serves the public profile and Inbox, `PublishAsync(listing, references)` (`PUT professionals/me`; references go only in the request, never back in a `ListingDto`) returns `PublishResult.PhoneTaken` for a number that already has a listing (anti-fraud rule 1: the listing number is the token's verified `phone_number`, unique in `Professionals`; no verified phone = `403 phone-required`), `RemoveAsync` takes the caller's listing out of search (Start over).

**App config** (data every page needs that may be hours stale: the trades and jobs, towns, price tiers, experience, urgency, income goals; one `AppConfig` model, one `ConfigDto`): loaded **once per launch, behind the splash** (`LaunchRouter` awaits `AppConfigService.LoadAsync()` before anything else), then held in memory by `ReferenceData` (`UseConfig`, guarded by `CanUse`: no empty list, every trade has jobs, the ids the code names exist). Pages never fetch it. The rules are the skeleton's generic **`RemoteConfig<T>`** (`MobileAppTheme/Services/RemoteConfig.cs`): the phone's copy (`config.json`, skeleton `FileConfigCache<T>` over `JsonFile<T>`, a `Stamped<T>` with `SavedAt` and the server's `Version`) is used with **no network call for 12 h** (`RemoteConfigRules.FreshFor`); after that the app asks `GET config` with `If-None-Match: <saved ETag>` (`ApiClient.GetIfChangedAsync`, no token) and the server answers **`304` with no body** when nothing changed (the copy counts as checked again) or `200` with the new config (saved); offline or slower than 8 s (`FetchTimeout`) it uses the stale copy, and with none it runs on `BuiltInConfig`. A server config that isn't usable is never used or saved. Server side `ConfigStore` keeps the config and its ETag (SHA-256 of the JSON) **12 h per instance** (`ConfigFor`; restart the Function App to apply a `004-config.sql` edit sooner, so an edit can take up to ~24 h to reach every phone) and `ConfigFunctions` sets `ETag` and `Cache-Control: public, max-age=43200`. **Why a JSON file and not SQLite:** it's one small document always read whole at launch; `JsonFile<T>` writes atomically (temp file, then move) and a corrupt file reads as missing, so the worst case is the built-in copy. Add SQLite only when local data needs querying. Ports: `IConfigSource<AppConfig>` and **`IOtherJobNoteRepository`** (both `Api/ApiConfigRepository`: `GET config`, `POST other-jobs`); **`OtherJobNotes`** (`Services/`, singleton) sends the typed "Others" text trimmed and cut to `MaxText` (= the server's `OtherJobNoteStore.MaxNote`), failures only logged. New stale-OK data goes into this same config (a `ConfigOptions` list or a new `ConfigDto` field), not a new endpoint.

### App shell (shared by both sides, after the interview)

- **`AppShell`** (skeleton, `MobileAppTheme/Components/Layout/`), Slack style: `AppTopBar` (brand name + logo from `AppBrand` on the left, the user's `PersonAvatar` on the right linking to their page, optional green status dot), an optional `Banner` strip that sticks under it, the page in the middle, `AppBottomNav` icon tabs (`AppTab`: href, icon, label, badge, `MatchPrefix` to keep a tab lit on its sub-pages), its height `--app-bottom-nav-height` (5.625rem, 1.5x its natural height; the page padding, `app-sticky-action` and `app-fab` are placed from it). Fixed parts use the `app-*` gap classes in the skeleton's `mobile-app-theme.css`; a page's main action sits last with `app-sticky-action` so it stays just above the tabs.
- The app wires the skeleton in three places: `MauiProgram` (`AddMobileAppTheme(AppTheme.Brand)`, then `IAppAccount`), `Components/Routes.razor` (skeleton `MainLayout` as default layout, its `NotFound` page, its assembly in `AdditionalAssemblies`) and `wwwroot/index.html` (`_content/MobileAppTheme/mobile-app-theme.css`). Skeleton namespaces are global (`GlobalUsings.cs` + `Components/_Imports.razor`).
- Each side has a thin layout that loads its workspace (non-matching users go back to `/`) and hands `AppShell` its tabs: **`Professional/ProLayout`** and **`Seeker/SeekerLayout`**. Pages opt in with `@layout`. Full-screen steps (`/professional/publish`, `/me/reviews/rate/{id}`) use `InterviewStep` instead, outside the shell.
- Routes live in `ProRoutes` / `SeekerRoutes`; link through them, never a literal path.

### Pro side (`Components/Professional/`)

- **`ProWorkspace`** (`Services/`, singleton) holds the pro's draft, photos, chats and reviews and the actions on them (add/remove photos, change own photo, publish, reply, mark a chat read); it raises `Changed` so the shell re-renders.
- Until the listing is published, `ProLayout` passes `AppShell.Banner` a `NotLiveBanner`: one purple line (`MudAlert` Info, text cut with "…", never two rows) "Di ka pa nakikita · Tapusin ang listing" that opens Pro home.
- Tabs: Home `/professional` (`SetupCard` checklist until published, collapsible `HomeSection`s, + button adds work photos), Inbox `/professional/inbox` (unread badge; each chat at `/professional/inbox/{chatId}`, `ProChatPage`: the customer, the job, what/where/when/budget, messages and a reply box), Reviews `/professional/reviews`, Me `/professional/me` (`ProMePage`, also the avatar: own photo, Edit listing, Publish, a link to work photos, card preview, then the shared `MePage` parts). Work photos live under Me at `/professional/me/photos` (2 to 6, shown two across in a sideways-scrolling `PhotoStrip`) and references at `/professional/me/references` (1 to 3), so the Me tab stays lit.
- Profile and work photos live on `ProfessionalDraft` (`ProfilePhotoId`, `WorkPhotoIds`, `PublishedAt`) and show on `ProCard` (avatar photo + the newest 3 work photos).
- **Publishing needs a complete listing** (`ProfessionalDraft.IsListingComplete`: trade, jobs, area, towns, experience, rate). `ProWorkspace.PublishAsync` returns `PublishResult.Incomplete` without sending, the photo auto-republish skips, and `PublishPage` sends the worker to `ProfessionalInterview.FirstUnansweredPath` (the interview opens its first unanswered question).
- **…and proof** (`ProfessionalDraft.HasProof`): a profile photo, at least `MinWorkPhotos` (2) work photos and at least `MinReferences` (1, up to `MaxReferences` 3) **references** (`WorkReference`: name + E.164 number; private: Seekers see only how many (`ListingDto.ReferenceCount` → `ProfessionalListing.ReferenceCount`, counted by SQL), never names or numbers, which are sent only in `PublishListingRequest.References` and stored in `ProfessionalReferences`). Otherwise `PublishAsync` returns `PublishResult.MissingProof` and `PublishPage` goes back to Pro home. The server checks the same (`ProfessionalStore.InvalidField`: `400 invalid-profilePhotoId` / `invalid-workPhotoIds` / `invalid-references`; a reference can't be the worker's own number or repeat one). Pro home's `SetupCard` ticks photo → work photos (n of 2) → reference → **confirmed number** (`ProWorkspace.HasVerifiedPhone`: the account's SMS-verified number; the step links to `/verify/phone?then=/professional`; always done when no sign-in provider is registered), then shows a **Publish and find work** button. **When the last step is done the app opens Publish by itself, once** (`ProWorkspace.IsReadyToPublish` / `TakePublishPrompt`, reset by `Forget`; `ProLayout` checks on each page change, after `RefreshAccountAsync` picks up a just-linked number, and on `Changed`), so Back from Publish doesn't bounce. The card stays (with a note, no button) for a listing published before proof was required, until it's done. A published listing can't drop below 2 work photos or 1 reference (`CanRemoveWorkPhoto`, `CanRemoveReference`), and the auto-republish runs only while `HasProof`. References live at `/professional/me/references` (`ReferencesPage`, `ReferenceForm`, `ReferenceRow`; `ProWorkspace.AddReferenceAsync` reads typed numbers with `PhilippineMobile` and returns a `ReferenceAddResult`).
- After the interview preview's Done, `ProfessionalInterview` shows a `WorkingLoader` ("Saving your listing…") while it saves the answers and the profile and loads `ProWorkspace`, so Pro home opens filled.

The pro answers in their own Inbox. Only pros the Seeker chatted with can be reviewed, from 24 hours after the first message. Shared chat parts live in `Components/Chats/` (`ChatHeader` with the Seeker's **Call** button on the right, `ChatBubble` (theirs gray, mine ink), `ChatComposer` (pill box + round send), `ChatRow`); each side wraps `ChatRow` (`SeekerChatRow`, `ProChatRow`), and `ChatText` (`Services/Localization/`) words the job for the pro.
- **Search relevance (`Services/Search/`)** — keep it explainable, every weight is a named constant:
  - `SearchText`: normalises typed words (lower case, accents off, English/Tagalog filler words dropped) and scores word matches (exact 1, typed prefix 0.8, longer form 0.7).
  - `SearchIntentParser`: free text → trade + (when one clearly fits) job, matched against both languages' category/job labels, category hints and `TradeWords` synonyms (tubero, kuryente, hinang, masahe…). Generic job words (sira, repair, install…) count half toward the trade; a tie or weak match returns no trade plus the closest ones, and the UI asks "which kind of pro?". Add a synonym to `TradeWords` when users type a word we don't catch.
  - `SearchRanker` (**server**, `SideGigPh.AzureSQL/SearchRanker.cs`, over `RankCandidate`s (a `ListingDto` + server-only `WorkerSignals`: chats received/answered in 90 days and average first-reply minutes from `Chats.ProfessionalRepliedAt`, `Users.LastActiveAt` (stamped at most hourly by `UserStore.TouchAsync` when a worker reads their Inbox), account age), with `RankScales` from the config; `RankedResult.Page(skip, take)`). Filters: **exact job only** (no fallback; `SearchPageDto.ServiceFallback` is always false, kept for old apps); grouped "goes to your town" then "other towns nearby" (= other towns in the Seeker's area; workers only in other areas are left out). Then a **0–100 score** inside each group (`RankScore`, every part a 0–1 feature × a named weight): reviews 30 (Bayesian stars 22 + log review count 8), responsiveness 20 (smoothed reply rate 12 + reply speed 8), activity 20 (weekly half-life 14 + tenure 6), budget fit 20, experience 10; new workers start from neutral priors. **Paid boosts are never part of the score**: they will be labeled sponsored slots placed after ranking, behind a quality floor. Full rationale and the boost plan: [`docs/search-ranking.md`](docs/search-ranking.md).
  - `ProfessionalSearch` (app) asks the server for one ranked page at a time (`SearchAsync` the first, `MoreAsync` the next after what is shown); a page that didn't load (offline) leaves the results as they are.

### Auth

Auth is provider-neutral. The contract and screens live in the skeleton; the vendor is an adapter in its own project.

- **Contract (skeleton, `MobileAppTheme/Auth/`):** `IIdentityProvider` (phone code, Google, current user, sign-out, and `Methods`, the `AuthMethods` it supports) with `AuthUser`, `AuthResult` and `PhoneVerification`. A failure is an **`AuthError`** (`Cancelled`, `Network`, `InvalidCode`, `InvalidPhoneNumber`, `PhoneInUse`, `TooManyAttempts`, `Misconfigured`, `NotAvailable`, `Unknown`) plus the provider's raw `Detail` for logs. The UI shows `AppText.Describe(error)` (`CommonCopy`, English/Taglish), never provider text.
- **Screens (skeleton, `MobileAppTheme/Components/Auth/`):** `AuthPage` (route **`/verify`**: brand + tagline, then only the methods the provider offers, phone first), `NamePage` (**`/verify/name`**, once when the account has no name), `AddPhonePage` (**`/verify/phone?then=…`**, links a verified number to the signed-in account), `PhoneSignIn` (`LinkToCurrentUser` for linking) and `GoogleSignInButton`. **`SignInGate`** (`MobileAppTheme/Auth/`) is what pages ask: it returns the missing step (sign in, name, phone) or null, and lets everyone through when no provider is registered. Routes are in `AuthRoutes`.
- **App hooks:** `IAuthLanding` says where to go after sign-in. SideGigPh's `Services/SideGigPhAuthLanding` sends a user with a Professional profile to `/professional` and anyone else to `/`, where the launch router resumes onboarding. `IPhoneNumberFormat` reads typed numbers into E.164; SideGigPh's `PhilippinePhoneNumberFormat` accepts 0917… / 917… / +63 917… and sets the optional `Region` ("Philippines (+63)"), shown read-only above the number like Airbnb's Country/Region box. Skeleton defaults (`TryAdd`): `NoIdentityProvider` (no sign-in, `Methods = None`), `HomeAuthLanding` (`/`) and `E164PhoneNumberFormat`.
- **Adapter: `MobileAppTheme.Firebase/`** (Android/iOS MAUI library, `Microsoft.NET.Sdk`, not Razor, so no WebView asset clash). `FirebaseIdentityProvider`, `FirebaseAuthErrors` (status-code decoding) and `FirebaseAuthSetup`: `builder.AddFirebaseAuth(GoogleWebClientId)` in `MauiProgram` initializes the SDK in the platform lifecycle (wrapped, so a missing config doesn't crash launch) and **replaces** the skeleton's `IIdentityProvider`. `GoogleWebClientId` (the web OAuth client, client_type 3, from `google-services.json`) is a constant in `MauiProgram`.
- **Auth error policy:** an adapter never reduces an auth-infra exception to a bare message. It logs the full exception (type + stack) to Logcat/Output and returns an `AuthResult` with a mapped `AuthError`. For Google sign-in, `FirebaseAuthErrors.FromGoogle` parses the Google Play status code out of the exception message (which is just `"7:"`, `"10: …"`), with no dependency on the Play-services binding: `7` → `Network`, `10` DEVELOPER_ERROR / `12500` → `Misconfigured`, `12501` → `Cancelled`. A wrong SMS code (`FirebaseAuthException` `InvalidCredential`) → `InvalidCode`. `SignUpWithPhoneAsync` logs then rethrows (fail fast). Phone sign-in checks the app with Play Integrity (the Play Integrity API must be on, `firebase/cloudshell-auth.sh`); on an emulator that always fails with 17028 "Invalid app info in play_integrity_token", so `AddFirebaseAuth` forces the reCAPTCHA check there (`DeviceType.Virtual`), never on a real phone.
- **Packages (in `MobileAppTheme.Firebase`, `PrivateAssets="none"` so their build targets reach the app and process `google-services.json`):** `Plugin.Firebase.Auth` 3.1.1 + `Plugin.Firebase.Auth.Google` 3.1.2 + `Plugin.Firebase.CloudMessaging` 3.1.2 (the **modular** packages — NOT the bundled `Plugin.Firebase`, which drags in Crashlytics and crashes at launch in MAUI). Android **requires** `MainActivity.OnActivityResult` to call `FirebaseAuthSetup.HandleActivityResult(...)`; without it `SignInWithGoogleAsync()` hangs forever (no exception, stuck on "connecting"). `HandleActivityResult` forwards only while a Google sign-in is pending (`GoogleSignInPending`): the photo picker's and dialer's results reach `OnActivityResult` too, and the plugin's handler throws a `NullReferenceException` (shown as `Android.Runtime.JavaProxyThrowable`) that kills the app when nothing is waiting. The app's debug/release **SHA-1 (and SHA-256 for phone auth) must be registered in the Firebase console** and `google-services.json` re-downloaded — otherwise Google sign-in returns `DEVELOPER_ERROR` (status 10) and phone verification fails app-attestation.
- **Android signing ([`docs/android-signing.md`](docs/android-signing.md)):** every build on every PC and in CI is signed with the committed shared dev key `Platforms/Android/Signing/dev.keystore` (alias `androiddebugkey`, password `android`; SHA-1 `A5:F0:C9:…:31:B6` registered in Firebase), so sign-in works everywhere without registering per-machine keys. A Release build switches to the store key only when `ReleaseKeystore` (or env `SIDEGIGPH_KEYSTORE`) points at an existing file. The passwords come from env `SIDEGIGPH_KEYSTORE_PASS` / `SIDEGIGPH_KEY_PASS` and are never in the csproj. Other keystores are git-ignored. CI writes `google-services.json` and the optional store key from secrets (`GOOGLE_SERVICES_JSON_BASE64`, `ANDROID_KEYSTORE_BASE64`, …). Google Play's App signing key needs its own fingerprints in Firebase.
- **Firebase config (not committed; required before an Android/iOS run):** `Platforms/Android/google-services.json`, `Platforms/iOS/GoogleService-Info.plist`, plus a Google OAuth client (Android SHA-1; iOS reversed-client-id URL scheme). The app's csproj references the config files with `Condition="Exists(...)"` so the build works without them.

#### Switching the auth provider

Nothing outside the adapter project and `MauiProgram` knows the provider is Firebase. To move to another one (Supabase, Azure AD B2C, Auth0, a custom backend…):

1. Create `MobileAppTheme.<Provider>/` next to `MobileAppTheme.Firebase/`: a class implementing `IIdentityProvider` with its `Methods`, mapping every failure to an `AuthError` (log the full exception first), and a `builder.Add<Provider>Auth(...)` extension that does its setup and `Replace`s `IIdentityProvider`. Load the `maui-firebase-auth` skill for the error policy and the `mobile-app-theme` skill for the boundary rules.
2. In `SideGigPh.Maui.csproj`, swap the `MobileAppTheme.Firebase` project reference for the new one; in `MauiProgram`, swap `AddFirebaseAuth(...)` for the new call; in `MainActivity`, remove the `FirebaseAuthSetup.HandleActivityResult` line (or replace it with what the new SDK needs).
3. Remove the Firebase config files and `GoogleWebClientId` if nothing else uses Firebase.
4. Users are keyed by `AuthUser.Uid`; the new provider's ids differ, so existing accounts need a migration (once there are real accounts).

Never call a provider SDK from a page, workspace or service. If the UI needs something the contract lacks (e.g. email sign-in), add it to `IIdentityProvider` / `AuthMethods` / `AuthError` in the skeleton first, then implement it in every adapter.

### Anti-Fraud Rules

These are hard business rules — never bypass them:
1. **1 Phone = 1 GCash = 1 Registration** — unique constraint, no duplicates. A listing's number must also not be another account's Job Seeker number (`ProfessionalStore.PublishAsync` → `409 phone-used-by-seeker`, `PublishResult.PhoneUsedBySeeker`); `Users.PhoneNumber` is always the token's verified number (`UserFunctions.Save` ignores the body's), so a profile can't claim someone else's
2. **Duplicate image detection** — SHA-256 or perceptual hash on portfolio uploads, reject duplicates

## Coding Standards

- **C# / .NET 10**, nullable enabled, implicit usings
- **Interfaces first** — define the port, then implement the adapter
- **No vendor lock-in** — Firebase, Azure, etc. must sit behind an interface
- **Mobile-first UI** — every component must work on phone-width viewports
- **Reusable, composable components** — build small, single-responsibility Razor components and compose them; never create one giant `.razor` page that does everything. Extract repeated or self-contained UI into its own component with `[Parameter]`-driven inputs and `EventCallback` outputs
- **Component folder structure** — group components by feature under `Components/<Feature>/`, and always use code-behind: each component is a `<Name>.razor` markup file paired with a `<Name>.razor.cs` partial class for its logic. Shared shell/layout components live under `Components/Layout/`
- **Skeleton vs app vs feature components** (load the `mobile-app-theme` skill to decide):
  - **Skeleton** (`MobileAppTheme/Components/Shared/`): generic UI any product would use unchanged, with no domain words: `InterviewStep`, `ChoiceTiles` (+ `ChoiceTile`, `ChoiceItem`), `WorkingLoader`, `PersonAvatar` (photo, initials on ink or a person icon), `BusyOverlay` (in the skeleton `MainLayout`: spinner + rotating word, `CommonCopy.Busy*`, while the `BusyIndicator` singleton is busy; pages wrap slow actions in `await Busy.RunAsync(...)`: publish, photo uploads, review, Start over), `SheetHeader` (✕/← + centered title + hairline) and `SheetPage` (full-screen sheet with that header: sign-in, name, add phone), `MenuRow` (settings-list row with chevron), `ProfileCard` (raised card: big photo, name, status), `HomeSection` (collapsible home section), `FilterMenu` (a chip with a dropdown that scrolls and shows `ChoiceItem.Group` headings: Search filters and the home town picker), `BrandMark` (logo + name from `AppBrand`), `LanguagePicker`, `LoadMoreOnScroll` (at a long list's growing end: spinner + `OnLoadMore` near that end or when the list is too short to scroll, via MudBlazor's scroll listener and scroll manager; `Edge` `Bottom` for results, `Top` for a chat: opens at the end and keeps the reader's place when older items go above), `StartOverCard` (confirm-twice Start over, optional `Warning`) and `MePage` (the Me page frame: title, the side's own sections, then `LanguagePicker`, the on-this-phone note and `StartOverCard`; SideGigPh passes its own `StartOverWarning`). The skeleton never references SideGigPh.
  - **App-generic** (`SideGigPh.Maui/Components/Shared/`): used by two or more SideGigPh features but tied to its domain: `TradeBadge` (the worker's trade as a purple `Variant.Text` chip, emoji + label, "❄️ Aircon Technician", on `ProCard` and the public profile's `ProfileHero`; shows nothing for a retired trade), `ProCard` (+ `ProCardFact`; one card for search results *and* the pro's own preview; results pass `Dense`: photo, name, trade + budget badge, one row of facts, so 3–4 fit on screen), `ListingFacts` and `ServiceChips` (the dense card; the public profile uses its own `ProfileStats` and `JobList`; all their text comes from `Services/Localization/ListingText`), `ReviewRow` + `RatingSummary`, `GoalPayoff`, `PhotoAddNotice` (why photos weren't added, on both Me pages and the work-photo pages), `PhotoStrip` (work photos two across, scrolling sideways past two: the public profile, before Reviews, and the work-photo page).
  - **Feature** components stay in their feature folder.
- **MudBlazor only, no raw HTML** — markup is built from MudBlazor components; don't write `<div>`, `<span>`, `<p>`, `<button>`, `<input>` etc. in `.razor` files. Use `MudStack` for layout and spacing (`Row`, `Spacing`, `AlignItems`, `Justify`, `Wrap`), `MudText` for all text (`Typo` for size, `HtmlTag="h1"` for headings — `FocusOnNavigate` focuses the page's `h1`), `MudContainer` for page width, and MudBlazor's own spacing/flex utility classes (`pa-4`, `flex-1`, `mud-width-full`…). Reach for the out-of-the-box component first (`MudButton`, `MudTextField`, `MudChip`, `MudAlert`, `MudCard`, `MudSkeleton`, `MudProgressLinear`…). Only when MudBlazor has no parameter or utility for something, add a small, named helper class in the "MudBlazor gaps" section of `MobileAppTheme/wwwroot/mobile-app-theme.css` (generic) or `SideGigPh.Maui/wwwroot/app.css` (SideGigPh-only). Scoped `.razor.css` files don't reach inside MudBlazor components, so don't add them. The only raw HTML is `wwwroot/index.html` (the pre-Blazor splash).
- **Bilingual copy (English / Taglish)**: never hard-code user-facing text in a component.
  - UI strings are `LocalizedText(English, Taglish)` pairs in `Services/Localization/Copy.cs`. Strings every app shares (Back, Next, Cancel, Start over, Language, "3 hr ago", Not Found) are in the skeleton's `CommonCopy`; use those instead of duplicating them. Answer lists (jobs, towns, prices…) are in `Services/ReferenceData.cs`.
  - Components inject `AppText T` (skeleton) and render `@T.Get(...)` / `@T.Format(...)`.
  - Write for low English literacy: short plain words, an icon on every choice tile, and numbers (₱, years) doing the work.
  - Taglish is everyday conversational Taglish, not formal Filipino. Use local lingo, not forced translation:
    - Keep the English technical terms (split-type, chemical wash, freon, breaker, inverter, PMS, CCTV, waterproofing).
    - Use the local words people actually say (CR, gripo, lababo, yero, alulod, kisame, semento, poso).
    - Use Pa-/Paki- only where it sounds natural.
  - Job labels stand on their own ("Linis ng aircon"), so they also read correctly inside the pre-filled SMS.
- **Theming / colors** — SideGigPh's name, logo icon, colors and corner radius live in `SideGigPh.Maui/Components/Layout/AppTheme.cs` (`AppTheme.Style`, a `BrandStyle`, and `AppTheme.Brand`, an `AppBrand`). **The logo** is a worker in a hard hat, one SVG path (`AppTheme.Logo`, the `AppBrand` logo icon drawn in `Color.Primary`); the same path is the launcher icon (`Resources/AppIcon/appiconfg.svg`, white on the purple `appicon.svg`), the native splash (`Resources/Splash/splash.svg`, purple on white) and the pre-Blazor splash in `wwwroot/index.html`, so a new logo changes all four. The skeleton's `MobileTheme.Create` turns them into the `MudTheme` (palette mapping + typography). The look is **clean and minimal, Airbnb style**: **no blue anywhere**, and a **60/30/10 palette**: ~60% white surfaces (white top bar with a hairline), ~30% near-black ink `#222222` (`Color.Dark`: text, icons, back buttons, own chat bubbles, avatars, unselected chips), ~10% the brand accent, deep purple `#5B2A86` (`Primary`, `Color.Primary`): logo, launcher icon, native splash and loading screen, filled main-action buttons (Next, Contact, Publish, Send, the FAB), the active tab, progress bars and spinners, selected tiles, checks and chips. Two fixed exceptions, never used for anything else: **stars are gold** `#FFB400` (`Color.Warning`, on every `MudRating` and the star fact) and **money is dollar green** `#118C4F` (`Color.Success`: the rate fact, the "Pasok sa budget" chip, plus "published" and done checks); **10+ years of experience** (`ReferenceData.TopExperienceId`, `listing.IsSeasoned()`) shows in the brand purple with the `WorkspacePremium` award icon (`ProCardFact`/`StatTile` `Highlight`); `ProCardFact.IconColor` picks them; red (`Color.Error`) for Start over, soft gray lines, 8px buttons, 12px fields and tiles, flat (no shadows except `app-raised` cards), big bold `Typo.h4` page/question titles. Interview steps and sign-in sheets center their content vertically when it is short, and each interview question has an emoji picture (`InterviewStep.Illustration`) above its centered title. Android draws dark status-bar icons on the white bar (`MainActivity.OnCreate`) and `MainPage` keeps the WebView out from under the status bar (`SafeAreaEdges="Container"`). Text fields use `Variant.Filled` + `app-field` (label inside the box; stack related ones in an `app-field-group`). `Secondary` is the muted gray, so `Color.Secondary` is the helper-text color; `Info` is the brand accent. Components pick colors only through MudBlazor's `Color` parameters; any rule in `app.css` uses the theme's `var(--mud-palette-...)` variables. Never hard-code hex in components or CSS (the one exception: the pre-Blazor splash fallbacks in `app.css`, which must match `AppTheme`). To restyle the app, change `AppTheme`.
- **No dead code** — delete unused code, don't comment it out
- Keep business logic in `SideGigPh.Shared` (when it exists), platform-specific code in `SideGigPh.Maui`, and only app-agnostic frame/UI/adapters in `MobileAppTheme`
- Any change to the project structure , architecture, design patterns, theme, design should reflect in this CLAUDE.md

## Build & CI

- GitHub Actions workflow at `.github/workflows/build.yml` (manual run)
- `.github/workflows/tests.yml` runs `SideGigPh.Tests` on `ubuntu-latest` with a SQL Server 2022 service container (`SIDEGIGPH_TEST_SQL`), on pushes and pull requests to `main` that touch code the tests see (not CSS, images, `.razor` markup or docs), by hand, and as a required first job of `deploy-api.yml` (no deploy unless every test passes). It fails if any test was skipped and writes a coverage summary to the run page.
- `.github/workflows/deploy-api.yml` builds and deploys `SideGigPh.Api` to the Function App `SideGigPhApi` (Flex Consumption, Linux, Southeast Asia) when run by hand (Actions → Run workflow). It signs in with OIDC as the user-assigned managed identity `sidegigph-github-deploy` (repo secrets `AZURE_CLIENT_ID`, `AZURE_TENANT_ID`, `AZURE_SUBSCRIPTION_ID`, made by `azure/cloudshell-github-deploy.sh`; trusts `main` only), so there is no publish profile; the app's own system-assigned identity is what reaches Azure SQL (setup: [`azure/README.md`](azure/README.md) → Automatic deploy from GitHub)
- Android builds on `ubuntu-latest`, iOS builds on `macos-latest`
- Both install .NET 10 + platform-specific MAUI workload
- Working directory for builds: `SideGigPh.Maui/`

## Common Commands

```bash
# Build Android
dotnet publish -f net10.0-android -c Release

# Build iOS (macOS only)
dotnet build -f net10.0-ios -c Release

# Restore workloads
dotnet workload install maui

# Run the tests (from the repo folder; integration tests need SQL Server LocalDB or SIDEGIGPH_TEST_SQL)
dotnet test SideGigPh.Tests

# Only the fast unit tests
dotnet test SideGigPh.Tests --filter "Category!=Integration"

# Claude / CLI with Visual Studio open: run in a throwaway copy (skips when only CSS/markup/docs changed)
bash .claude/skills/run-tests/scripts/run-tests.sh --changed
```

## Project Skills (`.claude/skills/`)

Load the matching skill before doing these tasks. Every folder in `.claude/skills/` is listed here; add a line when you add a skill, and remove it when you delete one.

**Building features**
- **`mobile-app-theme`**: anything in `MobileAppTheme/`, deciding skeleton vs app for a new component/service/model/CSS helper, promoting a component into the skeleton, rebranding, or starting a new app on the skeleton. Script: `skeleton-check.sh` (no app dependency, no domain words, `CommonCopy` keys).
- **`new-razor-component`**: any new, split-out or restyled `.razor` component, page, tab or route (folders, code-behind, the `AppShell` layouts and routes). Script: `ui-lint.sh` (raw HTML, hex, literal text, page h1s).
- **`mudblazor-ui`**: MudBlazor 9 markup, verified parameter/enum/icon/utility names, gap classes, theme. Script: `mud-api.sh`.
- **`ports-and-adapters`**: new stored data or a new port method, end to end: SQL script (+ seed), EF row/mapping, store, contract + `ApiJson`, function, app adapter, port, DI, workspace.
- **`db-migration`**: any table, column, index or constraint change on the live database: a new guarded `NNN-schema-<what>.sql`, never an edit to `001-schema.sql` or a drop-and-create. Scripts: `new-migration.sh` (next-numbered file from the template), `migration-check.sh` (001 unchanged, every step guarded, recorded in `SchemaChanges`).
- **`add-interview-step`**: adding or changing an onboarding question, or the flow and resume logic.
- **`onboarding-ux-review`**: UX critique against the onboarding research, plus trust guardrails (permissions, hooks, sign-up placement).
- **`maui-firebase-auth`**: Firebase phone OTP / Google sign-in behind `IIdentityProvider`, `google-services.json`, SHA-1, status codes 7/10/12501.

**Build, run and fix**
- **`run-tests`**: after a significant change to code the tests cover (app Services/Models, API, AzureSQL incl. SQL scripts, Contracts, skeleton C#, csproj): run `SideGigPh.Tests` in a throwaway copy and fix failures at the root cause, never by weakening a test. Not for CSS/markup/docs-only changes. Scripts: `run-tests.sh` (`--changed`, `--unit`, `--coverage`), `coverage-summary.awk`, `uncovered-lines.awk`.
- **`build-check`**: compile-check a throwaway copy after code changes (safe with Visual Studio open). Never build or deploy in the repo folder from the CLI.
- **`maui-build-troubleshooting`**: cancelled/locked builds, and a Debug app that dies on launch with "No assemblies found … Fast Deployment". Script: `fix-fast-deploy.sh`.
- **`android-emulator-vs-deploy`**: emulator with no internet, network errors only on the emulator, VS stuck on "Waiting for emulator".

**Manual only**
- **`update-skills`**: capture lessons from a session into these skills. Run only when the user asks.
- **`update-tools`**: turn repeatable checks, fixes or queries from a session into helper scripts in `skills/*/scripts/`. Run only when the user asks.
